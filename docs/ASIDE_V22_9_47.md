# V22.9.47 Lucian B 사용자 적용과 확인

이번 저장소 묶음은 웹 거래 목록과 삭제 취소입니다. PR #80 병합은 승인받아 완료했으며 B의 Git 게시와 운영 적용은 별도입니다. SQL·환경변수·Secrets·Kakao Developers·OpenBuilder·관제 Worker를 변경할 필요는 없습니다.

## 적용 절차

1. `VERIFICATION_V22_9_47.md`와 최신 main·B 변경 묶음의 CI를 대조합니다. 기존 운영 기록은 V22.9.44이지만 이번 실행에서 운영 상태를 다시 조회하지 않았으므로 실제 배포 버전과 되돌리기 기준을 확인합니다.
2. 게시·운영 적용이 승인된 실행에서 기존 `tools/deploy-worker-version.mjs` 도구로 검증한 전체 `src/index.js`를 업로드합니다. 저장 소스 해시·바인딩·런타임 설정을 대조한 뒤 별도 승인으로 승격합니다.
3. 개인 HTML을 새로 열어 셸·V5의 v22947 주소와 나머지 기존 자산 주소를 확인합니다. `/health`·`/ready`와 실제 로그인·권한 동작을 확인합니다. 이전 v22946 자산은 기존 바이트와 ETag로 계속 제공됩니다.

## 실제 기기 확인

iOS Safari, Android Chrome, 카카오톡 인앱 브라우저와 실제 VoiceOver·TalkBack에서 아래를 확인합니다. 자동 Chrome 검증은 실제 기기 확인을 대신하지 않습니다.

1. 거래 탭에서 분류·날짜·결제수단을 조합하여 결과를 0건으로 만듭니다. 제안이 최대 두 개이고 해제 후 같은 월·가계부·탭·나머지 조건이 유지되며 결과 건수와 초점이 전달되는지 확인합니다. 월 자체가 빈 경우에는 다른 안내가 나오고 조회 전용에는 기록 추가 행동이 없어야 합니다.
2. 테스트 거래의 삭제 버튼을 누릅니다. 행이 접히고 5초 대기 알림이 나오며 합계는 그대로인지 확인합니다. 되돌리기를 누르면 기록과 초점이 돌아오고 서버 기록이 유지되어야 합니다.
3. 알림 위 포인터 또는 되돌리기 버튼 초점으로 대기 시간이 멈추는지 확인합니다. 다른 거래 상세·일별 팝업을 다시 열어도 되돌리기에 접근할 수 있고 팝업만 닫으면 대기가 유지되어야 합니다.
4. 취소하지 않은 삭제는 서버 확인 뒤 완료로 표시되고 최신 목록·합계를 불러와야 합니다. 대기·요청 중 다른 삭제 버튼의 비활성화 이유를 확인합니다.
5. 대기 중 다른 페이지·가계부·월로 이동하거나 페이지를 닫습니다. 아직 전송하지 않은 삭제가 취소되는지 확인합니다. 뒤로 돌아와 타이머가 다시 시작되지 않아야 하며, 삭제를 사용하지 않은 설정·예산 화면의 미저장 입력은 B 때문에 다시 로드되지 않아야 합니다.
6. 운영 데이터에서 네트워크를 끊어 응답 유실을 일부러 만들지 않습니다. 승인된 테스트 환경에서 권한 변경·세션 만료·응답 지연·유실을 확인하며 결과 불명확이면 자동 재전송이 없고 해당 ID만 재삭제가 차단되는지 확인합니다. 현재 기록 조회는 현재 존재·부재만 안내하고 이번 요청의 성공·실패로 단정하지 않아야 합니다.
7. 같은 탭으로 돌아왔을 때 불명확한 요청을 확인할 수 있는지 검사합니다. 가계부 ID가 URL에 없는 별도 거래 수정 화면에서도 결과 확인 안내가 나오고 같은 기록의 재삭제가 차단되어야 합니다. 브라우저 저장소를 사용할 수 없는 경우에도 취소나 요청 실패가 중복 전송을 만들지 않아야 합니다.
8. 라이트·다크·네 색상, 확대·작은 화면, 44px 터치 영역, 움직임 줄이기, 금액 가리기를 확인합니다. 새 삭제 알림에는 금액·메모를 표시하지 않으며 빈 결과 제안은 건수만 표시합니다.

1280px 다크의 기존 알림 개수 배지 대비 1.90:1은 변경 전 E에서도 재현한 후속 감사 항목입니다. 새 B 요소의 자동 대비 검증과 구분하여 기록합니다.
