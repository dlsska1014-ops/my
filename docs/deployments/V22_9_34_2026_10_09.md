## Signup failure cause (added 2026-10-10)

The agent analysed the failed signup above and confirmed the cause offline. The fix is `V22.9.35-SIGNUP-KDF-FIX` (`00_READ_FIRST_V22_9_35.md`, `docs/ASIDE_V22_9_35.md`).

- **Cause:** password hashes use PBKDF2-SHA256 with `PASSWORD_KDF_ITERATIONS = 210000`, unchanged since V22.7.2. The Cloudflare Workers production runtime rejects PBKDF2 above 100,000 iterations with `NotSupportedError`; this is the workerd default cap. Node.js and open-source workerd have no such cap, so every repository check passed.
  - workerd [issue #1346](https://github.com/cloudflare/workerd/issues/1346) is still open and includes a January 2026 report of an error at 210,000 iterations on Workers.
  - [PR #7550](https://github.com/cloudflare/workerd/pull/7550), which would raise the default cap to 1,000,000, is not merged.
- **Reproduction:** with the in-memory fixture rejecting PBKDF2 above 100,000 like the production runtime, a signup on the V22.9.34 code returns HTTP 500 with the same message, 「계정을 만들지 못했습니다. 잠시 후 다시 시도해 주세요.」
  - It creates no `users` row and no local identity.
  - It records `local_signup_failed / error / signup_failed; Pbkdf2 failed: iteration counts above 100000 are not supported (requested 210000).`
- **Account A:** the hash is computed before the account-creation RPC, so the failed signup almost certainly created no account. The read-only query ① in `docs/ASIDE_V22_9_35.md` section 2 confirms this without reading credential fields.
- **Not a V22.9.34 regression:** V22.9.34 did not change the signup path. Its only authentication changes were the logout card and the strict admin-password read. The risk had been recorded as unverified since V22.9.30 in `KNOWN-ISSUES.md`.
- **Same cause elsewhere:** local signup, a Kakao user's ID/password setup (`/my/backup-login`) and the admin password change always failed in production. A login with an unknown name returned 500 instead of 401. Kakao login and Kakao chatbot records were unaffected.
- **Event detail:** operation events are kept only in the memory of each Worker isolate (the last 220 events). The 23:43:56 KST event can no longer be read; the reproduction shows the detail it would have held.
- **Primary key:** the section 2 constraint query above returned `transactions_pkey / p / PRIMARY KEY (id)`. The schema requirement of the explicit-id saves (B13) is therefore met. The insert path itself still needs a signed-in save, which follows the V22.9.35 signup check.
