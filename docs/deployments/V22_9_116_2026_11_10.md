## 설계
- P-1: ‘방금’ 대상 = 마지막 저장 기록(created_at 순 limit 1, 내 기록 조건)과 마지막으로 바뀐 내 기록(updated_at 순 limit 1, 같은 조건)을 Promise.all 로 함께 읽는다. 둘이 다르고 바뀐 시각 > 저장 시각(마이크로초까지; 읽지 못하는 시각은 두 값이 다르면 바뀐 것으로 본다)이면 `{ row: null, ambiguousText }` 를 돌려 세 호출처(삭제·값 수정·번호 없는 지출자 변경)가 아무것도 바꾸지 않고 되묻는다. 되묻는 글: ‘마지막에 저장한 뒤에 다른 기록을 고쳐서 ‘방금’이 어느 기록인지 정하지 못했어요. 아무것도 바꾸지 않았어요.’ + 마지막에 고친 기록(다른 날이면 ‘7월 14일’ 같은 날짜 앞머리) + 마지막에 저장한 기록(한 번에 여러 건이면 최대 6줄) + ‘번호로 보내 주세요. 예: 수정 NN번 금액 13000 / 삭제 NN번’(번호가 없으면 ‘오늘기록’ 안내).
- P-2: 서버는 소비 분석 자료에 `started`(householdStartYmd(가계부) = 만든 날 KST, 모르면 빈 값)와 정기 자동 기록 줄의 8번째 칸 1(isRecurringSourceRow)을 넣는다. 클라이언트 noSpendDaysIn(start, end): 그 기간에 직접 적은 기록이 없으면 null(칩 없음), 시작 날 = started(그 기간에 더 앞선 기록이 있으면 그 날), from = max(기간 첫날, 시작 날) ~ min(기간 끝, 오늘)에서 금액 > 0 지출이 없는 날 수. 서버 buildLivingReport·noSpendDaysFrom 과 같은 규칙이다. 관리자 두 화면은 calculateDashboardAnalysis 에 startedOn = householdStartYmd(가계부, 행)을 넘긴다.
