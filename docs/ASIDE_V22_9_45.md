# V22.9.45 사용자 배포와 운영 확인 절차

이 작업에서는 운영에 요청하거나 배포하지 않았습니다. 앱 Worker 전체를 `V22.9.45-DEFERRED-SAVE`로 교체할 준비를 마쳤습니다. SQL·환경변수·Secret·바인딩·관제 Worker·Kakao Developers·OpenBuilder 변경은 필요하지 않습니다.

## 1. 배포할 소스 확인

PR의 Ubuntu·Windows × 일반·분류 표 부재 CI를 확인하고 PR을 병합합니다. 병합된 커밋에서 추적 파일 변경이 없는 작업 트리를 준비합니다. 다음 검사가 통과하고 판 번호·실제 검사 수·체크섬 수·소스 SHA-256이 `VERIFICATION_V22_9_45.md`와 일치해야 합니다.

```powershell
node .codex/scripts/verify-repository.mjs
npm run validate:categories-absent
node monitoring/test-d1.mjs
git diff --check
```

## 2. 업로드, 대조, 승격

기존 `CLOUDFLARE_API_TOKEN`과 `CLOUDFLARE_ACCOUNT_ID` 또는 `CF_ACCOUNT_ID`를 사용자가 자신의 환경에 설정하여 실행합니다. 토큰을 명령 인자·로그·문서·Git에 기록하지 않습니다.

```powershell
node tools/deploy-worker-version.mjs
```

이 명령은 버전을 업로드하고 바인딩·런타임·소스·내보내기를 대조합니다. 출력한 새 버전 ID와 `output/deploy/V22.9.45-DEFERRED-SAVE/`의 로컬 대조 기록을 확인합니다. 현재 운영 기준은 V22.9.44 버전 `3d12b754-299f-4e83-8235-c5994d7fa4f9`, 배포 `4d5884dd-1a12-408a-93b9-d934e6c71bae`입니다.

업로드와 승격 사이에는 Secret·바인딩·운영 배포를 변경하지 않습니다. 현재 배포와 설정이 업로드 당시의 대조 기록과 같은지 사용자가 확인한 뒤 승격합니다. 아직 수정하지 않은 감사 항목 G-4 때문에 이 수동 확인이 필요합니다. 기준이 달라졌으면 승격을 중단하고 최신 상태에서 업로드·대조를 다시 수행합니다.

```powershell
node tools/deploy-worker-version.mjs --promote <새_버전_ID>
```

승격 뒤 소스 SHA-256 일치, `/health` 5회 연속 판 일치와 공개 검사가 통과하는지 확인합니다. `/ready`의 판 번호와 준비 상태도 확인합니다. 선택 표 `accountbook_categories`가 없는 상태는 유지합니다.

## 3. 실제 카카오 기록 확인

1. 새 테스트 단톡방에서 소유자가 `점심 51000`을 보냅니다. ‘처리 중’으로 답해도 같은 내용을 다시 보내지 않고, 1분 안에 `오늘 기록 보기`에 정확히 1건이 표시되는지 확인합니다.
2. 같은 방의 두 번째 사람이 `커피 4700`을 보내면 구성원으로 참여하고 정확히 1건을 저장하는지 확인합니다.
3. 소유자가 `구성원 권한 기록만`을 보낸 뒤 구성원의 새 기록은 저장되고 구성원의 수정·삭제는 거절되는지 확인합니다.
4. 새 1:1 계정으로 `점심 53000`을 보내 개인 가계부에 정확히 1건 저장되는지 확인합니다. ‘처리 중’ 응답 뒤에는 `오늘 기록 보기`로 확인합니다.
5. 확인이 끝나면 사용자가 기존 관리 기능으로 테스트 거래·가계부를 정리합니다. 과거에 누락된 실제 거래를 자동 재작성하지 않습니다.

먼저 답한 새 방의 소유자에게 초기 권한 안내가 추가로 전송되지 않습니다. 저장 결과는 `오늘 기록 보기`, 권한은 `구성원 권한`으로 확인합니다.

## 4. 관리자와 관제 확인

관리자 세션에서 `/?legacy=1`과 `/admin-view`를 확인합니다. 올바른 날짜 필터가 동작하고, 잘못된 날짜나 `</script><script>window.__x=1</script>`를 URL 인코딩한 `date` 값은 빈 날짜로 처리되어 스크립트가 실행되지 않아야 합니다.

OpenBuilder의 ‘스킬 서버 연결 오류’ 메일이 멈췄는지 확인합니다. `/ops-monitor`에서 새 정상 기록의 분류 표 부재가 DB 실패로 집계되지 않는지 확인합니다. 기존 사고 표본은 삭제하지 않으므로 ‘최근 처리 실패 기록’ 경고가 24시간 집계 범위에서 해소되는지 봅니다. 다른 실제 실패가 있으면 경고가 계속될 수 있습니다.

후속 저장 실패의 관제 전송 G-5는 이번 범위에 포함되지 않습니다. Free CPU 한도와 실제 카카오 전달 성공 여부도 운영에서 확인합니다.

## 5. 되돌리기

새 판의 문제가 운영에 영향을 주면 사용자가 직전 V22.9.44로 되돌립니다.

```powershell
node tools/deploy-worker-version.mjs --rollback 3d12b754-299f-4e83-8235-c5994d7fa4f9
```

이미 저장한 거래는 남습니다. V22.9.44에는 B-1·C-1이 남아 있으므로 복구 뒤에는 해당 위험을 다시 고려합니다.
