# V22.9.38 운영 기능·실기기 확인용 Aside 지시문

아래 지시문을 Aside에 전달합니다. 2026-10-10에 배포된 `V22.9.38-LIVING-REPORT`를 대상으로 합니다. 코드 배포 절차가 아니라 이미 배포된 서비스의 기능 확인 절차입니다. 이 문서의 체크박스는 아직 실행하지 않은 항목입니다. 실제 결과는 별도 QA 기록에 남깁니다.

이 문서는 새 실행에도 사용할 수 있는 공통 절차입니다. 이미 시작한 검증을 이어갈 때는 최신 QA 기록과 비공개 `ASIDE-이어하기.txt`의 완료 상태를 먼저 확인하세요. 통과한 자료를 다시 만들지 말고, 고정된 예시 합계 대신 각 단계 직전의 실제 건수와 금액에 그 단계의 증감을 적용하세요.

현재 사용자는 카카오 기능을 코드로 검증하도록 방향을 바꿨습니다. 로컬 연속 검증 135개가 일반·분류 테이블 부재 모드에서 각각 통과했고, 운영 A 계정의 로그아웃도 완료됐습니다. 아래 카카오·실기기 절차는 나중에 사용자가 실제 기기 확인을 요청할 때 적용하는 참고 지시문입니다. 현재 요청의 필수 사용자 입력이나 카카오 참여 요청으로 다시 안내하지 마세요.

## Aside에 전달할 지시문

말해가계부 운영 주소 `https://malhaebook.com`에서 아래 검증을 순서대로 진행해 주세요. 기존 테스트 계정 A·B는 Aside Vault에 저장되어 있습니다. 이전 `V22934 점검` 가계부는 삭제되었으므로 재사용하지 않습니다. 계정 A·B 자체는 남아 있습니다.

기존 사용자 데이터와 계정 연결을 보존해 주세요. 비밀번호는 Vault 자동 입력이나 사용자 직접 입력으로만 사용하고, 대화·파일·스크린샷에 기록하지 마세요. 자격 증명을 찾을 수 없으면 사용자에게 해당 로그인 화면의 직접 입력만 요청하세요. 별도 계정 생성이나 비밀번호 변경으로 우회하지 마세요.

### 1. 테스트 범위를 먼저 고정해 주세요

- 별도 테스트 브라우저에서 계정 A로 로그인하세요. 기존 사용자가 작업 중인 브라우저 탭의 세션을 바꾸지 마세요.
- 실행 식별자 `S=YYYYMMDD-HHmm`을 KST로 정하세요. 가계부 목록에서 `V22938 점검 S`라는 새 가계부를 만들고 표시 이름을 `점검A`로 입력하세요.
- 생성한 가계부의 이름과 URL에 나타난 `household_id`를 기록하세요. 이 값을 `H`, 선택 월을 `M`이라고 부릅니다. URL의 인증 코드나 토큰은 기록하지 마세요.
- 처음에는 거래 0건·지출 0원이어야 합니다. 이후 저장·수정·삭제 전마다 이름과 H가 같은지 확인하세요. 예상하지 않은 기록이나 참여자가 보이면 중단하세요.
- 테스트 범위는 H와 이번에 만든 테스트 기록으로 제한하세요. 실제 사용자 가계부는 조회하여 내용을 수집하거나 수정하지 마세요. 보호 여부는 테스트 가계부의 보존 행과 작업 범위로 확인하고, 전체 운영 DB를 대조했다고 주장하지 마세요.
- SQL, 직접 DB/API 쓰기, Secrets, 환경변수, Kakao Developers, OpenBuilder, Worker 재배포, 계정 통합, 가계부 영구 삭제는 실행하지 마세요. 운영 장애를 강제로 만들거나 통신을 가로채는 시험도 하지 마세요.

### 3. 계정 B와 참여 권한을 확인해 주세요

W7에서 로그아웃했다면 이후 검증을 시작하기 전에 A로 다시 로그인하고 H를 확인하세요. 이 단계는 A와 B를 구분할 수 있는 별도 세션 두 개가 준비되었을 때 실행하세요. 초대코드는 로그인 비밀번호와 다르며 결과 보고나 캡처에 공개하지 마세요.

- [ ] A가 H의 초대코드를 확인하고 B가 참여 요청을 보냅니다. A는 테스트 계정 B만 `구성원 · 기록 가능`으로 승인합니다.
- [ ] B가 KEEP 행을 조회할 수 있지만 A의 거래를 수정·삭제할 수 있는 UI는 제공되지 않는지 확인합니다.
- [ ] B가 오늘 날짜·현금 지출 700원·내용 `V38QA-S-B-KEEP` 한 건을 저장합니다. W5 성공 시 전체 결과는 2건·지출 1,900원입니다. W5를 취소했다면 3건·지출 4,400원입니다.
- [ ] A가 B를 `조회 전용`으로 바꾸고 B가 새로고침합니다. 조회는 가능하지만 거래와 카드 목표 저장 UI는 제공되지 않아야 합니다. 직전 단계에서 확인한 모든 행은 그대로 남아야 합니다.
- [ ] 역할 검증이 끝나면 B를 검증 시작 때 합의한 테스트 역할로 돌리고, 최종 역할을 기록합니다. 다른 참여자의 권한은 변경하지 않습니다.

버튼이 없다는 사실만으로 서버의 모든 권한 검사를 통과했다고 기록하지 마세요. 세션을 분리할 수 없거나 B의 로그인이 준비되지 않으면 이 단계는 `NOT-RUN`으로 남기세요.

카드 별칭에는 긴 날짜·시각 숫자를 붙이지 마세요. 실제 운영 확인에서 그런 별칭이 카드번호 보호 규칙에 걸려 거절되었습니다. 입력 오류 후에는 이름뿐 아니라 종류와 모든 입력값을 다시 확인하세요. 재표시된 폼은 기본 종류인 입출금·통장으로 돌아갈 수 있습니다. 등록 결과에 `신용카드`가 표시되는지 확인한 다음 목표 검증을 진행하세요.

필수 설정이나 기간 기록 조회가 실제로 실패하면 정상 합계처럼 판정하지 마세요. 실패 화면을 기록하고 중단하세요. 실패를 강제로 만들지 못했으면 로컬 장애 검증과 구분하여 `NOT-RUN`으로 남기세요.

### 5. 실제 카카오 계정으로 테스트 가계부 연동을 확인해 주세요

먼저 전용 테스트 카카오 계정인지, 기존 실사용 계정인지 구분하세요. 2026-10-10 후속 확인에서 사용자는 기존 실사용 계정만 있다고 답했습니다. 이 경우에는 말해가계부를 이미 이용 중인지 먼저 확인하고, 진행 중인 대화를 마친 뒤 기존 선택 가계부를 사용자가 개인적으로 기록하게 하세요. 테스트 가계부 H의 참여·기록만 확인하고 끝나면 기존 선택 가계부로 되돌리세요. 참여 이력은 남으므로 모든 계정 상태가 그대로라고 보고하지 마세요. 기존 선택이 없으면 H에 참여한 상태로 선택만 비우는 UI는 확인되지 않았으므로 완전 복원을 보장하지 마세요. 서비스 첫 이용이면 가입 범위를 확정하기 전 명령을 보내지 마세요.

시크릿 브라우저나 새 웹 계정만으로 카카오 계정이 분리되는 것은 아닙니다. 기존 실사용 카카오 계정을 A·B에 연결하거나 계정을 통합하지 마세요. 아래 OAuth 로그인 연결 시험은 전용 테스트 계정이 있을 때만 적용합니다. 일반 카카오 로그인도 서비스 사용자·식별자 상태를 갱신할 수 있으므로 읽기 전용 검사로 설명하지 마세요. 기존 단톡방에서는 시험하지 마세요.

카카오 OAuth 로그인 식별자 연결과 챗봇의 1회용 웹 연결 코드는 서로 다른 기능입니다. 하나가 성공했다고 다른 하나도 통과한 것으로 기록하지 마세요.

1. 테스트 카카오 계정으로 서비스의 실제 1:1 대화를 열고 `시작`을 보냅니다. 필요한 경우 `가계부 참여 <H의 초대코드>`로 요청하고 A가 그 테스트 참여자만 승인합니다.
2. `가계부 전환`에서 H를 선택한 뒤 다시 `시작`을 보내 테스트 가계부명과 기록 가능한 권한을 확인합니다. 웹에서 H를 골랐어도 카카오의 선택은 별도로 확인해야 합니다.
3. 현재 거래 건수를 적고 `커피 100원 연동점검가`를 한 번 보냅니다. 지출 100원 저장 답장과 날짜·번호를 확인합니다. 웹의 H에서도 한 건만 증가해야 합니다.
4. `월급 100원 연동점검나`를 한 번 보내 수입 100원 한 건이 추가되는지 확인합니다. 카카오 두 건의 합계는 지출 100원·수입 100원입니다.
5. 실제 답장에 나온 날짜와 번호를 사용하여 `○월 ○일 수정 NN번 금액 200`을 보냅니다. 지출 기록만 200원이 되어야 하며 새 거래가 추가되면 안 됩니다.
6. 날짜·번호·메모가 일치하는 그 지출만 삭제합니다. 삭제 답장과 웹의 감소 건수를 확인한 뒤, 답장에 표시된 정확한 `복구 NN번` 명령을 보냅니다. 200원 기록 한 건이 복구되어야 합니다. 번호를 추측하거나 번호 없는 `방금 삭제`로 대체하지 마세요.
7. 선택 가계부를 다시 확인하고 `택시 7`을 보냅니다. 단위를 요구하며 저장하지 않아야 합니다. `택시 7원`은 7원으로 한 건 저장되어야 합니다. 이 추가 기록도 테스트 목록에 남깁니다.
8. 1:1에서 `웹 가계부 열기`를 요청합니다. 별도 테스트 브라우저의 `카카오에서 기록한 가계부 이어 열기`에 코드를 입력하면 같은 카카오 기록 계정으로 웹 세션이 전환되어야 합니다. 계정 병합은 아닙니다. 전환 후 H와 위 기록을 다시 확인합니다.
9. 같은 코드를 다시 사용하는 요청은 거절되어야 합니다. 코드는 10분·1회용이며 재발급하면 이전 코드가 무효화됩니다. 코드·초대코드·OAuth URL의 인증값은 캡처와 보고에서 가리세요.

응답이 늦거나 저장 여부가 불확실하면 문장을 바꿔 재전송하지 마세요. 웹의 H에서 먼저 저장 여부를 확인하고 KST 시각·명령 종류·응답 지연·성공 여부를 기록하세요. 1회 성공만으로 카카오의 모든 요청이 5초 안에 끝난다고 판단하지 마세요.

#### OAuth 로그인 연결은 별도로 확인해 주세요

- 연결할 웹 계정을 A·B·카카오 코드로 전환한 계정 중 정확히 하나로 정하고 현재 웹 세션이 그 계정인지 다시 확인하세요. 앞선 웹 코드 사용으로 세션이 바뀌었을 수 있습니다. 테스트 웹 계정에 이미 카카오가 연결되어 있는지도 확인하고 기존 연결을 교체하지 마세요.
- **연결 버튼을 누르기 전에**, 그 브라우저의 현재 카카오 로그인 세션이 사용자가 지정한 전용 테스트 계정임을 확인하세요. 확인할 수 없으면 `NOT-RUN`으로 중단하세요. 기존 쿠키와 동의가 있으면 동의 화면 없이 콜백에서 연결될 수 있으므로, 연결 화면을 연 뒤 계정을 확인하는 방식으로 대신하지 마세요.
- 테스트 전용 카카오 계정이 확인되었을 때만 `내 계정·보안`의 카카오 로그인 연결을 엽니다. 로컬 계정의 현재 비밀번호 입력은 Vault 또는 사용자가 수행합니다.
- 동의 화면에 표시된 계정·앱·권한을 사용자와 확인하고, Aside가 요구하는 동의·보안 접근 승인 단계는 사용자에게 맡기세요. 예상과 다른 계정이나 권한이면 취소하세요.
- 완료 후 별도 테스트 세션에서 카카오 로그인 → 서비스 콜백 → 같은 테스트 계정·H·기록 조회를 확인하세요. 취소 경로에서는 계정과 기록이 바뀌지 않아야 합니다.
- KOE006·다른 계정 연결·인앱 재인증 제한이 나오면 메시지를 남기고 중단하세요. 콘솔 설정이나 Secret 변경으로 우회하지 마세요.

#### 단톡방은 전용 테스트 방이 있을 때만 확인해 주세요

- 실제 사용자가 있는 방을 시험 대상으로 삼지 마세요. 봇 호출이 가능한 전용 방과 테스트 참여자가 준비된 경우만 진행하세요.
- 봇을 실제로 멘션하고 `단톡방 연결 <H의 초대코드>` 및 `시작`으로 H 연결을 확인하세요. 기존 연결을 바꾸라는 안내가 나오면 중단하세요.
- 고유한 테스트 거래 한 건을 보내 웹 H에서 한 건만 증가하는지 확인하세요. 그룹 답장에 QuickReplies·CommerceCard·Carousel이 없어야 하며, 개인 웹 연결 코드가 노출되면 안 됩니다.
- 별도 미연결 방의 첫 거래는 공동 가계부를 자동 생성할 수 있습니다. 이 기본 검증에서는 실행하지 말고, 필요하면 해당 테스트 방·생성 범위를 별도로 확정한 뒤 진행하세요.
- 봇 호출이 불가능하거나 그룹 권한이 없으면 `NOT-RUN`으로 기록하세요. OpenBuilder의 합성 요청을 실제 카카오 단톡방 검증으로 대신하지 마세요.

### 7. 종료와 결과를 남겨 주세요

- 테스트 계정과 H는 후속 확인을 위해 보존하세요. 자동 정리나 가계부 영구 삭제를 하지 마세요. 삭제 검증 대상 이외의 테스트 잔존 기록·카드·권한을 목록으로 남기세요.
- 사용자가 별도로 정리를 요청하면 이번 실행 식별자 S에 속한 정확한 대상만 UI에서 정리하세요. 삭제 후 복구를 보장하지 마세요.
- 테스트 세션을 로그아웃하고, 사용자가 입력 중인 창은 임의로 닫지 마세요.
- 각 항목을 `PASS`, `FAIL`, `NOT-RUN`, `BLOCKED`로 구분하세요. `PASS-PC`, `PASS-DEVICE`, `USER-CONFIRMED`처럼 근거를 덧붙일 수 있습니다. 미실행을 통과로 처리하지 마세요.
- 결과에는 KST 시각, 기기·OS·브라우저, 테스트 가계부의 식별 정보, 단계, 기대값, 실제 값, 새로고침 후 건수·합계, 민감정보를 가린 증거, 남아 있는 테스트 데이터를 적으세요. 공개 Git 기록에는 실제 로그인 이름·가계부 ID·초대코드·연결 코드·사용자 데이터를 넣지 마세요.
- 이상이 생기면 영향 범위를 넓히지 말고 첫 실패와 마지막 확정 성공 단계를 보고하세요. 별도 승인 없이 운영 재배포·롤백·SQL 수정을 실행하지 마세요.
