# V22.9.128 후속 발견 기록 — 운영 웹 확인 (2026-11-17)

V22.9.127(수입·지출 고르기 단추)을 main 에 넣은 뒤(2026-11-17 18:53 KST), 사용자가 사람 확인 목록 가운데 웹 쪽을 Aside 로 대신 보게 했다("웹 확인도 aside 통해서 진행해줘").
확인에 쓴 브라우저에는 말해가계부 세션도 카카오 로그인 세션도 없어, 로그인 없이 열리는 화면만 볼 수 있었다. 거기서 두 가지가 나왔고(W-1·W-2) 이 판은 그 둘만 고친다.
시험 단톡방의 ‘웹 가계부 열기’ 로 로그인 없이 들어가 보려던 길에서 본 것(W-3·W-4)과 보지 못한 것(W-5)도 적는다. SQL·Secret·운영 변수는 없다.

## 발견

### W-1 로그인 전 /start-guide 의 ‘접기’ 단추가 눌러도 아무 일이 없음 (P3, 고침)
- 본 것(운영, 390 폭): 제목 아래 안내 문장 밑에 기본 모양의 [접기] 단추가 보이고, 눌러도 아무것도 접히지 않았다(aria-expanded 도 true 그대로).
- 까닭: 머리말 안내문을 접는 칸(V22.9.9)은 화면 후처리가 머리말 표식(abV5PageHeader)만 보고 붙인다. 단추를 움직이는 코드(bindHeadNotes)는 테마 스크립트에,
  모양은 셸 스타일시트의 `body.abV22812Shell .abHeadNote …` 규칙에 있는데, 그 둘은 사용자 셸 화면에만 실린다. 로그인 전 /start-guide 는 셸이 없는 화면인데 머리말 표식이 있어 단추만 생겼다.
- 범위(오프라인, 공개·사용자 주소 114개와 관리자 주소를 로그인 상태 넷으로 훑은 응답 404개): ‘접기’ 가 있는 응답 60개 가운데 스크립트가 없는 것은 로그인 전 /start-guide 둘(주소 꼴 둘)뿐이었다.
- 고침(`src/modules/web/html-postprocess.js` attachUiUxRuntime): 테마 스크립트·셸 스타일시트·바탕 표식(abV22812Shell)이 모두 있는 화면에만 접는 칸을 만든다.
  로그인 전 /start-guide 는 안내 문장이 제목 아래 그대로 보인다. 로그인한 화면들의 접는 칸은 그대로다(같은 훑기에서 58개).
- 왜 못 봤나: 화면 점검(V22.9.124·125)은 이 화면을 로그인한 상태로만 쟀고, 공개 화면 훑기는 사이트맵의 주소만 봤다(/start-guide 는 사이트맵에 없다).

### W-2 없는 주소 화면의 제목이 휴대폰에서 낱말 가운데에서 꺾임 (P3, 고침)
- 390 폭에서 ‘페이지를 찾을 수 없습니 / 다.’ 로 꺾였다. 낱말 단위 줄바꿈(`word-break:keep-all`)을 넣어 ‘페이지를 찾을 수 / 없습니다.’ 로 꺾인다(`src/modules/public/site-config.js` pageNotFoundResponse).
  문구·두 링크·색인 금지 표식은 그대로다.

### W-3 단톡방 ‘웹가계부’ 답 카드의 [웹 가계부 열기] 가 로그인 없이 바로 열리지 않음 (P2, 결정 필요)
- 본 것(운영 시험 단톡방, PC 카카오톡 → 기본 브라우저, 세션 없음, 2026-11-17 두 번): `웹가계부` 의 답 카드("… 아래 버튼을 누르면 이 방 가계부가 열려요.")에 달린 [웹 가계부 열기] 를 누르자
  가계부 홈이 아니라 `/my` 시작 화면이 열렸다. 두 번째에는 열린 탭의 넘김 횟수를 읽었다 — 0번(주소에 덧붙은 값도 없음).
- 뜻: 화면 요청에 카카오의 식별 값(botUserKey·appUserId·botGroupKey)이 하나라도 있으면 서버는 반드시 한 번 넘긴다(값을 뺀 주소로 303 — 운영에서 `/faq?botUserKey=…` 로 확인).
  넘김이 0번이면 그 링크에는 값이 붙지 않았다. 로그인 없는 바로 열기(V22.9.105)는 그 값이 있어야 시작된다.
- 왜: 카카오 그룹 챗봇 안내서는 이 기능이 "블록의 응답 설정에서 버튼에 URL 링크를 설정하면" 동작한다고 적는다. 2026-11-07 에 PC 에서 바로 열렸던 것은 봇 입장 카드의 [웹가계부](오픈빌더 블록에 고정으로 둔 URL 단추)였다.
  `웹가계부` 의 답 카드는 스킬(서버)이 만든 단추다. V22.9.105 는 두 단추 모두에 값이 붙는다고 보고 만들었고(`kakao/response-builders.js` 의 주석), 스킬 답의 단추로는 운영에서 확인한 적이 없었다.
- 지금 상태: 2026-11-12 에 봇을 추가한 시험 방의 입장 카드는 "환영해요! 말해가계부예요. …" 와 [도움말 보기]·[기록하기] 둘뿐이라 웹 단추가 없다. 그래서 새 방에는 식별 값이 붙는 웹 단추가 없다.
  카카오톡 안의 브라우저는 자동 로그인(V22.9.91)으로 들어가고(카카오 로그인을 써 본 사람은 화면 없이, 처음이면 카카오 동의 화면을 거친다), PC 카카오톡이 여는 바깥 브라우저에서는 시작 화면이 나온다.
- 확인하지 못한 것: 휴대폰 카카오톡에서 스킬 답의 단추에 값이 붙는지, 오픈빌더 블록의 URL 단추가 지금도 값을 받는지(이 방에는 그런 단추가 없어 누르지 못했다), 운영의 진단 기록(`kakao_room_open_probe_v229105:*` — 마지막 ‘ok’ 의 시각과 판, 운영 DB 읽기라 따로 지목이 필요하다).
- 고칠 곳은 오픈빌더다(이 판은 바꾸지 않는다): `웹가계부` 말을 받는 블록의 응답에 URL 단추를 고정으로 두거나(스킬은 그대로 불러 방 가계부 준비·참여가 되게), 입장 카드에 [웹가계부] URL 단추를 다시 둔다. 카카오 콘솔 변경과 배포는 사용자 결정이다.
- 이 기록의 첫 판에 적었던 추정(‘강한 식별이 붙은 계정이라 V22.9.118 S-2 의 설계대로’)은 틀렸다 — 그 갈래는 값이 붙은 링크에서만 탄다. 값이 붙은 링크라도 카카오 로그인·로그인 이름이 붙은 계정은 PC 에서 시작 화면이 나온다는 점은 그대로다(S-2).

### W-4 답 카드의 단추로 들어와 로그인하면 그 방 가계부가 아니라 기억된 가계부가 열릴 수 있음 (P3, 남음)
- 답 카드 단추의 주소는 `/my` 이고 방 가계부 번호가 없다(V22.9.105 때는 채팅 계정과 웹 로그인 계정이 이어지지 않아, 번호를 넣으면 ‘가계부를 찾을 수 없어요’ 가 될 수 있어서 뺐다).
  식별 값 없이 들어와 로그인하면(자동 로그인 포함) 그 계정의 기억된(기본) 가계부가 열린다. 가계부가 하나인 사람은 같은 가계부다.
- 식별 값이 붙은 링크에서 카카오 로그인이 붙은 계정이 PC 로 올 때도 같다: 세션이 없는 `/app?household_id=…` 는 가계부 번호 없이 `/my` 로 간다(오프라인 확인). 로그인 이름 비밀번호만 붙은 계정은 return_to 로 그 방 가계부에 돌아온다(V22.9.118).
- 로그인 흐름이라 출시 뒤 후보로 둔다.

### W-5 운영의 로그인 뒤 화면·관리자·관제 화면은 자동으로 확인하지 못함 (P3, 확인 불가)
- 확인에 쓴 브라우저에 말해가계부 세션이 없었고, 사이트의 카카오 로그인을 눌러도 카카오가 아이디·비밀번호를 물어 거기서 멈췄다(직접 입력하지 않는다). 관리자 비밀번호도 넣지 않는다.
- RELEASE-CHECKLIST 의 V22.9.124~126 사람 확인(웹)과 관제 1.8.0 화면 확인이 그대로 남는다. 운영자가 그 브라우저에 로그인해 두면 같은 확인 목록을 다시 돌릴 수 있다.

## 결함이 아닌 것으로 본 것
- 첫 화면(/)에 ‘접기’ 가 없다는 보고: 접는 칸은 로그인한 화면의 머리말 안내문에만 있다(확인 지시의 기대가 틀렸다).
- /start-guide 에 꼬리말(사업자 정보·이메일 링크)이 없다는 보고: 이 화면과 /quick-input-help 는 사이트맵에 없는 안내 화면이고 예전부터 공개 꼬리말을 달지 않았다.
- /privacy 6절·8절 표: 390 폭에서 카드 모양으로 보이고 화면이 옆으로 밀리지 않았다(맞음).

## 검사
- 새 검사 `validation/validate-v229128-web-check.mjs`: 로그인 전 /start-guide 에 접는 칸이 없고 안내 문장·시작 단추·순서 안내가 그대로인지, 로그인한 열여섯 화면의 접는 칸이 그대로 하나인지,
  로그인 상태 넷으로 훑은 모든 응답에서 "단추가 있으면 테마 스크립트·셸 스타일시트·바탕 표식이 다 있다" 가 지켜지는지, 두 자산에 묶는 코드와 꾸미는 규칙이 실제로 있는지, 없는 주소 화면의 낱말 단위 줄바꿈.
  고치기 전 코드(V22.9.127)에서는 로그인 전 /start-guide 와 없는 주소 화면 단언이 실패한다.
- 화면 응답 대조(V22.9.127 ↔ 이 판, 주소 × 로그인 상태 넷 = 응답 418개, 판 이름을 가리고 견줌): 같음 348, 다름 70 = 로그인 전 /start-guide 2 + 없는 주소 화면 68.
- 화면 측정(헤드리스 Chrome, 390·768·1440): 로그인 전 /start-guide 의 44px 미만 조작 요소 1 → 0, 가로 스크롤·대비 미달·이름 없는 조작 요소 0 그대로.
- 라우터의 모든 주소 훑기(원본에 적힌 주소 395개 × 로그인 상태 넷 = 응답 1,580개, HTML 1,184개 가운데 200 이 아닌 것 513개): ‘접기’ 가 있는 응답 101 → 99, 스크립트나 스타일 없이 붙은 것 2 → 0.
  앞 판과 다른 응답은 로그인 전 /start-guide 2 + 없는 주소 화면 508 뿐이다(그 밖의 4개는 /health 의 시각).
- 기존 검사의 허점 하나를 고쳤다: `validation/validate-v229126-monitor.mjs` 의 12번(앱 /ops-monitor 가 관제 화면을 그대로 낸다)은 관제 호출이 정확히 한 번이라고 셌는데,
  앱은 사용자 요청의 표본(무작위 2%, 느리거나 실패한 요청)을 같은 연결의 `/internal/telemetry` 로 보낸다. 표본이 섞이면 호출이 둘이 돼 실패했다(이 판의 CI 에서 한 번 — 네 실행 가운데 하나가 실패하고 나머지는 취소됨).
  화면을 가져오는 호출만 세게 했다. 무작위를 0 으로 고정해 모든 요청에 표본을 보내게 하면 고치기 전 단언은 실패하고 고친 단언은 통과한다. 다른 관제 검사들은 무작위를 고정해 두어 해당이 없다.
- CI 의 실행 한도를 10분에서 20분으로 올렸다(`.github/workflows/verify.yml`): 윈도우 실행이 9분~9분 55초까지 늘어, 이 판의 CI 에서 윈도우 실행 하나가 10분 한도에 걸려 취소됐다(검사 실패가 아니다). 필수 검사 넷의 이름과 내용은 그대로다.
- 독립 검토(Claude API) 한 번: P1 0·P2 0·P3 3, "병합해도 됩니다". P3 셋을 반영했다 — 새 검사가 단추를 잃는 회귀를 느슨하게 잡던 것(→ 셸이 실린 머리말 화면에 접지 않은 안내 문장이 남지 않는다는 거꾸로 방향 단언과 단추 수 고정),
  코드 모양을 고정하던 단언(→ 조건이 세 가지를 보는지와 단추를 만드는 글이 그 조건 아래에만 있는지), 훑기 범위(→ 위의 모든 주소 훑기와 200 이 아닌 응답). 반영분은 다시 검토받지 않았다.

## 운영에서 확인할 것(배포 뒤)
- 로그인하지 않은 브라우저에서 /start-guide 를 열면 [접기] 단추가 없고 안내 문장이 그대로 보이는지. 로그인한 화면(예: 수입·예산)의 [접기] 는 그대로 접히는지.
- 없는 주소(예: /no-such-page)를 휴대폰 폭으로 열면 제목이 낱말 단위로 꺾이는지.
