## 호출 수

`app.fetch`가 응답을 돌려준 시점과 수집한 모든 `waitUntil`이 끝난 시점을 구분한다. 표의 값은 답 전/전체 호출 수다. 같은 장면과 같은 개수의 단언을 두 분류 모드에서 실행하며 호출 수에 비례하여 검사 개수를 늘리지 않는다.

| 장면 | 내용 | 분류 표 있음 | 분류 표 없음 |
|---|---|---|---|
| A | 새 방·첫 사용자 | 29/36 | 29/36 |
| B | 같은 방·같은 사용자 둘째 기록 | 9/11 | 8/10 |
| C | 셋째 기록 | 9/11 | 8/10 |
| D | 새 참여자 첫 기록 | 24/30 | 23/29 |

B의 픽스처 파동은 두 모드 모두 5이며 독립 DB 묶음은 네 단계다. 고정 상한은 B 답 전 10·전체 12, A 답 전 30, D 답 전 25, F 답 전 14다. **원래 F는 아직 실패한다.** 최초 별칭 등록을 답 뒤로 옮기는 B-0을 제외한 현재 범위와 F 상한의 적용 대상을 사용자가 결정해야 한다. 기존 별칭으로 원래와 같은 일반 입력을 보내면 11/13회이고, 강한 입력은 최초 17/19·기존 별칭 10/12회다.

합성 or+embedding 거절의 첫 요청은 일반 답 전 11회이며 지원 부재를 기억한 뒤에는 10회다. 모든 embedding이 없는 별도 조건은 일반 14/16·분류 표 없음 13/15회다. 이 별도 상한을 주 장면 B의 상한과 혼동하지 않는다.

## 보호 동작

120초 중복 범위, 90초 메시지 잠금, pending 표식 CAS와 거래 전송 순서, 새 구성원 지출자 번호, source_user_key와 user_id의 서로 다른 역할, 일일 500행 경계, 재연결 후 다른 가계부 스냅숏 폐기, waitUntil 없는 동기 호출을 검사한다. S2/HM 조회 실패는 저장을 거절하고 미리 얻은 메시지 잠금을 정리한다.

연속 요청 검사는 수집한 waitUntil을 명시적으로 기다린다. 별도 즉시 연속 요청은 정리가 끝나기 전 잠금이 새 저장을 막고, 정리 뒤 재시도하면 정확히 한 건을 저장하는지 확인한다. 생애주기 잠금은 복구 경로에서 사용자→방→가계부 순서를 유지하며 local mutex도 DB 잠금 해제가 처리될 때까지 기다린다. 남은 DB 호출이 1회이면 선택 작업을 생략하고 메시지 잠금을 해제하며, 해제 실패·예산 소진 시에도 local gate가 영구히 잠기지 않는다.

기존 V31 잠금 경쟁 검사는 미완료 준비 복구 경로로 명시했다. 빠른 기존 구성원 경로의 생애주기 경쟁 창은 KNOWN-ISSUES에 남긴다. V45는 더 빨라진 첫 방 준비가 여전히 응답 한도를 넘도록 250/300ms 지연을 주입하여 지연 답·완료·중복 방지 검사를 유지한다.

## 검증 상태와 근거

관련 검사와 전체 실행 로그는 저장소 밖 `review-artifacts/v100-k1-db-calls-2026-11-04/`에 보관한다. V100 F의 상한 실패를 숨기거나 전체 하네스 통과로 표시하지 않는다. 최종 검사 개수와 하한은 F 결정 뒤 두 모드 실측으로 갱신한다.

- 실제 전체 하네스 두 모드는 manifest 769개와 Worker 문법 검사에 통과한 뒤 F의 답 전·전체 상한에서 실패했다(`full-present-f-pending.log`, `full-absent-f-pending.log`). 신규 검사는 A~K 모든 상한과 추가 회귀를 실행하고 마지막에 F 실패 두 건을 함께 보고한다. 최소 기준 61,891개는 이전 판 값을 임시로 유지했다.
