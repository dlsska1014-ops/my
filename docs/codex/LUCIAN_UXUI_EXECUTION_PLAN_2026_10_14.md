## 3. B 거래 목록과 삭제 취소

### B1 빈 검색 결과

- 첫 적용 대상은 기존 필터가 있는 거래 목록입니다. 통합검색 API에 새 분류·기간 필터를 추가하는 작업은 포함하지 않습니다.
- 선택 월에 이미 읽은 거래를 이용해 날짜·분류·결제수단 등 적용 중인 조건을 하나씩 해제했을 때의 결과를 계산합니다. 원본 데이터의 완전성이 확인될 때만 정확한 건수를 표시합니다.
- 최대 두 가지 제안을 표시합니다. 예를 들어 `분류 조건 해제 · 8건` 버튼을 누르면 그 조건만 해제하고 가계부·거래 탭·나머지 조건·선택 월을 유지하며 페이지 번호를 초기화합니다. 분류 조건은 `category`와 `category_text`를 함께 해제합니다. 화면 예시의 건수를 제품에 고정하지 않습니다.
- 해제해도 결과가 없는 조건은 추천하지 않습니다. 하나만 해제해서 결과가 생기는 후보가 없으면 `이 달의 전체 기록 보기`를 제공합니다. 월 전체 기록이 없는 경우와 필터 때문에 결과가 없는 경우를 구분합니다. 조회 실패는 빈 결과로 처리하지 않습니다.
- 이 단계에서는 다른 달까지 기간을 확대하거나 추가 COUNT 요청을 보내지 않습니다. 목록 조회 횟수의 증가 목표는 0회입니다.
- 권한이 있는 사용자에게만 기록 추가 행동을 제공합니다. 필터 해제 후 결과 수를 알리고 키보드 초점이 사라지지 않도록 합니다.

주요 경로는 `src/modules/my/mobile-home.js`의 거래 필터·목록, 관련 클라이언트 함수와 셸 CSS입니다. 기존 인계 문서의 통합검색 대상 선정과 추가 COUNT 2회 설계는 이 단계에 적용하지 않습니다.

### B2 삭제 대기와 되돌리기

- 거래 단위 삭제 버튼에 먼저 적용합니다. 스와이프와 다중 선택은 후속 범위입니다. 가계부 삭제·탈퇴 등의 확인 절차는 유지합니다.
- 상태는 `표시 중 → 삭제 대기 → 요청 중 → 성공 / 명확한 실패 / 결과 확인 필요`로 구분합니다.
- 삭제를 누르면 화면에서 해당 행을 접고, `5초 후 삭제 · 되돌리기`를 표시합니다. 서버에 요청하기 전에는 삭제 성공이라고 알리지 않습니다.
- 되돌리기는 전송 전 대기를 취소하는 기능입니다. 서버에서 이미 삭제한 기록을 복원하는 새 API를 도입하지 않습니다.
- 첫 구현은 한 화면에서 한 건씩 처리합니다. 삭제 대기·전송 중에는 다른 삭제 버튼을 일시적으로 비활성화하고 이유를 알립니다. 다음 항목을 눌렀다는 이유로 앞 항목의 취소 시간을 줄이지 않습니다. 대기 중에는 확정 합계를 변경하지 않습니다.
- 되돌리기에 포커스하거나 알림에 포인터를 올린 동안에는 대기 시간을 멈춥니다. 같은 거래를 다시 누르면 중복 대기와 중복 요청을 만들지 않습니다.
- 대기 중 다른 페이지로 이동하거나 페이지를 닫으면 아직 전송하지 않은 삭제는 취소합니다. 알림에 이 동작을 안내합니다. 팝업만 닫는 것은 페이지 이동이 아니므로 공용 알림에서 대기를 유지합니다.
- `pagehide`에서 삭제를 자동 확정하지 않습니다. `pageshow`와 뒤로 가기 캐시 복귀에서는 취소한 타이머를 되살리지 않고 서버 목록과 다시 맞춥니다. `keepalive`나 `sendBeacon`을 성공 보장으로 취급하지 않습니다.
- 요청한 뒤에는 되돌리기 버튼을 비활성화하고 진행 상태를 알립니다. 서버 확인 후에만 완료를 알리고, 명확한 실패에서는 행을 복원합니다.
- 타임아웃·응답 유실·`db_write_unknown`에서는 자동 재전송하지 않습니다. 같은 가계부와 거래 ID를 기준으로 한 번 재조회하고, 확인할 수 없으면 `삭제 결과를 확인하지 못했습니다`와 재조회 행동을 제공합니다. 기록이 현재 존재해도 지연 중인 삭제가 실패했다고 단정하지 않으며, 부재만으로 이번 요청의 성공을 단정하지 않습니다. 건수 제한이 있는 일별 목록은 부재 판정에 사용하지 않습니다.
- 결과가 불명확한 거래의 삭제 재실행은 막고, 다른 거래의 삭제는 다시 허용합니다. 화면 전체가 계속 잠기지 않도록 결과 확인 상태와 전송 상태를 구분합니다. 정확한 ID 재조회 경로는 구현 시 기존 경로를 조사하여 재사용하거나, 같은 가계부의 현재 존재 여부만 반환하는 최소 읽기 경로로 준비합니다.
- 요청 전송 직전에는 가계부 ID·거래 ID·진행 상태만 `sessionStorage`에 보관하여 같은 탭으로 돌아왔을 때 결과 확인이 필요한 요청을 알립니다. 금액·메모는 저장하지 않습니다. 저장소 접근 실패가 삭제를 중복 실행하게 해서는 안 됩니다.
- 기존 삭제 경로의 가계부·역할·CSRF·감사 이력 검사를 재사용합니다. 명시적인 `Accept: application/json` 요청 분기에서 인증 만료·권한 거절·검증 실패·성공·불명확 상태를 구분하되 기존 HTML 폼의 리다이렉트 동작을 보존합니다. HTML 응답에서도 불명확한 결과를 `기존 기록 유지`로 확정하는 문구는 바로잡습니다. 최종 HTTP 200만으로 삭제 성공을 판단하지 않습니다.

주요 경로는 `src/modules/client/v5-bundle-mains.js`, `src/modules/admin/transactions-households.js`, 관련 사용자 조회 경로와 셸 CSS입니다. 목표 화면의 지연 저장 코드는 참고하되 요청 전 완료 문구와 페이지 종료 시 전송을 그대로 복사하지 않습니다.

**완료 기준:** 조건 하나만 해제되는지, 목록 조회가 늘지 않는지, 전송 전 취소 시 쓰기가 0회인지, 정상 확정 시 거래별 쓰기가 1회인지 확인합니다. 연속 삭제·권한 변경·페이지 이동·뒤로 가기 복귀·서버 거절·응답 유실을 각각 검사합니다.

## 4. A 빠른 입력 결과 확인

- `어제 점심 12,000원 국민카드`의 해석 결과를 날짜·금액·지출/수입·분류·결제수단 칩으로 표시합니다. 메모는 기존 입력칸에서 확인합니다.
- 칩은 별도의 저장 데이터가 아니라 현재 입력칸 값을 반영합니다. 누르면 필요한 상세 영역을 펼치고 해당 입력칸에 초점을 옮깁니다. 수정 결과는 칩에도 즉시 반영합니다.
- 기존 수동 수정 보존과 금액·날짜 오류 안내를 유지합니다. 해석되지 않은 항목을 확정된 값처럼 표시하지 않으며, 잘못된 파서를 칩으로 보완했다고 간주하지 않습니다.
- 금액 버튼은 `+1천 · +5천 · +1만 · +5만 · 지우기`를 제공합니다. 기존 천 단위 구분 기능을 재사용하고 입력 커서·붙여넣기·모바일 키보드 동작을 유지합니다.
- 예산 초과는 안내하되 지출 기록을 막거나 금액을 잘못된 입력으로 표시하지 않습니다. 실제 금액 형식 오류와 구분합니다.
- 숫자가 굴러가는 장식과 #081 저장 영수증은 이번 단계에서 제외합니다. 영수증을 추후 구현할 때에는 저장된 거래 ID로 확인해야 하며, 거래일 기준 최신 1건을 방금 저장한 기록으로 사용하지 않습니다.

주요 경로는 `src/modules/client/shared-input-parsers.js`, `legacy-ui-runtime.js`, `v5-bundle-mains.js`, `src/modules/my/mobile-home.js`입니다. 파서 자체 수정은 감사 2-A와 구분하며, 관련 A-01·A-02·A-03·A-05·A-06·F-1·F-2의 현재 결과를 확인합니다.

**완료 기준:** 칩과 실제 제출 값이 일치하고, 사용자가 수정한 값이 다시 파싱할 때 의도치 않게 덮어써지지 않아야 합니다. 날짜·수입/지출 변경, 예산 초과, 잘못된 금액, 입력 중 커서 이동, 지우기, 조회 전용 권한을 검사합니다.

## 5. D 예산 편집 중 합계

- 예상 수입 합계, 계획한 지출 합계, 계획상 차액을 입력 중 갱신합니다. `저장 전 미리보기`로 표시하고 기존 저장 버튼으로 확정합니다.
- 계획상 차액을 실제 계좌 잔액이나 현재 사용할 수 있는 돈으로 부르지 않습니다. 저장된 예산 요약과 편집 중인 계획을 구분합니다.
- 서버의 분류 정규화·중복 처리·빈 행·0원 규칙과 같은 결과를 계산합니다. 현재 같은 분류와 같은 금액은 한 번만 반영되고, 같은 분류의 서로 다른 금액은 거절되는 규칙을 재확인합니다.
- 잘못된 숫자를 0으로 바꾸어 합계를 만들지 않습니다. 중복 충돌이나 유효하지 않은 행이 있으면 해당 행을 안내하고 합계를 확정하지 않습니다.
- 추가 DB 요청과 자동 저장을 도입하지 않습니다. 계산 결과 안내가 숫자를 입력할 때마다 화면 읽기 프로그램의 발화를 방해하지 않도록 갱신을 묶습니다.

주요 경로는 `src/modules/my/settings-page.js`, `groups-budget-bulk.js`, `src/modules/admin/budget-center-recurring.js`, 관련 예산 도메인 함수입니다. 감사 2-C와 D-4가 정한 최종 분류·예산 규칙을 기준으로 삼습니다.

## 6. D 가져오기 열 연결과 재분석

- 첫 범위는 제목 행이 있는 표 형식 파일입니다. 원본 열과 날짜·금액·수입/지출 구분·수입금액·지출금액·내용·분류·결제수단·지출자·무시의 연결을 편집하는 화면을 제공합니다. 자연어 입력과 제목 없는 표는 기존 경로를 유지합니다.
- 자동으로 인식한 열뿐 아니라 인식하지 못한 열도 표시합니다. 제목이 같아도 열 인덱스로 구분하고 원본 값의 일부를 확인할 수 있게 합니다.
- 기존 `type`·`income`·`expense` 처리와 통화·원문 등 편집 대상이 아닌 매핑을 보존합니다. 사용자가 바꾼 연결만 덮어쓰고, 화면에 노출하지 않은 기존 매핑을 지우지 않습니다. 연결을 바꾸지 않은 재분석은 기존 분석과 같은 결과여야 합니다.
- 필드별 기존 파서 규칙에 따라 필수 필드 누락과 중복 연결을 검증합니다. 중복 연결을 해제할 때까지 재분석을 막는 경우에는 이유와 해결 방법을 표시합니다.
- 사용자가 `다시 분석`을 누르면 서버에서 원본과 연결 규칙으로 다시 계산하고 새 미리보기 토큰을 발급합니다. 클라이언트 표의 글자만 바꾸지 않습니다.
- 현재 토큰에는 원본 표 전체가 없으므로 원본 파일을 현재 탭에서 보관하고 재분석 요청에 다시 제출하는 방식을 우선 검토합니다. 새 업로드 보관소나 장기 브라우저 저장소를 만들지 않습니다. 필요한 원본이 없으면 재선택을 안내합니다.
- 서버는 열 인덱스·필드 허용 목록·파일 크기·행 수·연결 수를 검증합니다. 가계부 범위·사용자 권한·CSRF·토큰 만료 규칙을 유지합니다.

- 감사 E-1을 먼저 확인합니다. 같은 사용자 경로의 E-2·E-3·E-4·E-5·E-6·E-9·E-10·E-11·E-12·E-13·E-14·E-15는 최신 수정 여부와 회귀 사례를 대조하되 관리자 전용 감사 전체를 이 묶음에 포함하지 않습니다.

주요 경로는 `src/modules/my/backup-import.js`, `src/modules/import/flexible-import-parser.js`와 해당 화면의 클라이언트 코드입니다.

**완료 기준:** 미인식 열·중복 제목·필수 열 누락·중복 필드·잘못된 연결 요청을 검사합니다. 구분과 단일 금액이 있는 파일, 입금액과 출금액이 분리된 파일, 통화 열이 있는 파일은 연결을 바꾸지 않고 재분석해 기존 결과와 대조합니다. 연결 수정 → 재분석 → 새 토큰 → 선택 저장의 결과가 일치해야 하며, 토큰 만료·다른 가계부·중복 저장·상한 크기 파일의 CPU 회귀를 확인합니다.
