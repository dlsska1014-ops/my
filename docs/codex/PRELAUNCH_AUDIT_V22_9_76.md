# V22.9.76 출시 전 점검 (2026-10-21)

## 계기

운영자가 ‘수당’을 정기 수입으로 등록했는데 웹 알림이 “수당 납부 N일 전 · 월 X원 준비”처럼 정기지출 문구로 나왔다.
V22.8.79 에서 정기 항목에 수입(`type: income`)을 더할 때 정기 항목 화면과 카카오 정기 알림 문구만 바꾸고, 알림 센터
(`api/user-api.js`)·홈 안내와 카드·리포트의 ‘30일 안에 나갈 적립 계획’은 구분을 보지 않는 지출 전용 문구로 남았다.

## 한 일

1. 정기 수입 알림 버그를 고치고(R), 같은 종류의 문제를 세 갈래로 점검했다: 카카오 답장·안내(K), 웹 화면(W), 돈 계산·정기 반영·가져오기(M).
   다시 확인해 보니 결함이 아닌 것은 O 로 적었다.
2. 2026-10-14 감사(`AUDIT_FINDINGS_V22_9_44.md`) 105건의 재현 스크립트를 2026-10-21 코드에 다시 돌렸다: 재현 72 · 고쳐짐 29 · 판단 불가 4.
   재현된 것 중 심각한 것부터 이번 판에서 고쳤다.
3. 모든 항목의 상태를 `FINDINGS_LEDGER.md` 한 곳에서 추적하고, `validation/validate-findings-ledger-v22976.mjs` 가 빠진 항목을 막는다.
   상태별 건수는 추적표 머리에 있다.

## 왜 지금까지 잡히지 않았나

1. **값을 더할 때 그 값을 읽는 화면을 다 찾지 않았다.** 정기 항목에 수입을 더했지만 알림 센터·홈·리포트·카카오 요약은 구분을 보지 않았다.
2. **검사가 동작보다 소스 문자열을 봤다.** 기존 검사 다수가 `source.includes("…")` 로 특정 문장이 소스에 있는지만 본다. 문장이 있어도
   다른 경로가 틀린 말을 하면 통과한다. 예: 웹 D-24 수정은 ‘첫 가계부로 대체하지 않는다’는 V22.9.17 검사를 그대로 통과하면서 그 규칙을 뒤집었다
   (그 검사의 확인이 `|| true` 였다). 이번 판의 새 검사는 화면과 카카오 답장을 실제로 그려서 본다.
3. **검사 장면이 실제 사용과 달랐다.** 검사 데이터에 정기 수입·미래 날짜 기록·같은 이름 가계부가 없었다. 예약 반영 검사는 가계부 1,001개를
   만들고도 실행 한 번이 호출 한도를 지키는지만 봤고, 한 달 내내 매일 돌렸을 때 빠지는 항목이 없는지는 보지 않았다
   (가계부 32개·지정일 28일이면 11월에 10건이 빠졌다).
4. **감사 결과를 끝까지 추적하지 않았다.** 10-14 감사 105건 중 감사 번호를 달고 고친 것은 V22.9.45 의 5건이고, 나머지는 문서에만 남았다.
   정기지출 안내의 예시 문장이 오늘 지출로 저장되는 문제(A-11)도 그때 이미 적혀 있었다.

## 바꾼 일하는 방식

- 감사 문서를 쓰면 `FINDINGS_LEDGER.md` 에 항목을 모두 옮기고 상태(고침·일부 고침·남음·결정 필요·확인 불가·결함 아님)를 적는다. 검사가 항목 수를 대조한다.
- 이번 판부터 ‘고침’으로 적는 코드 결함은 하네스에 등록된 동작 검사를 함께 적는다. 새 검사는 옛 코드에서 실패하는 것을 확인한 뒤 넣는다.
- 구분(`type`)처럼 여러 화면이 읽는 값을 더하거나 바꾸면, 그 값을 읽는 곳을 grep 으로 모두 찾고 수입·지출을 둘 다 넣은 장면으로 검사한다.
- 기존 검사의 기대값을 바꾸는 수정은 커밋에 이유를 적고 합치는 사람이 따로 확인한다. 이번 판에서 기대값을 바꾼 곳: 웹 D-24(기억한 가계부를
  열 수 없으면 첫 가계부로 대신 열지 않고 고르는 화면으로), 돈 D-4(시작 분류 ‘교통’이 택시·주유까지 셈), 돈 E-4(기준을 보내지 않은 이번 달
  가져오기는 183일 규칙).
- 시간에 따라 쌓이는 동작(예약 반영·월말·새 달)은 실행 한 번이 아니라 여러 달을 매일 돌리는 모의 실행으로 검사한다.

## 예약 자동 반영을 바꾼 내용 (M-1·D-1·D-10)

- 가계부를 5개씩 넘기던 커서를 없앴다. 지정일이 지났고(말일 보정) 그 달 반영 표시가 없는 켜진 규칙을 저장소에서 바로 고른다
  (`is_active=not.is.false`, `or=(last_applied_month.is.null,last_applied_month.neq.<달>)`, `day_of_month=lte.<오늘>`, 500행씩).
- 40개 묶음마다 참여자 확인 → 기존 기록 확인 → 한 번에 저장 → 반영 표시. 결과를 모르는 저장(응답 유실·5xx)이 나오면 그 자리에서 멈추고
  표시를 바꾸지 않는다. 다음 실행이 기존 기록 확인과 고유 색인(`transactions_recurring_identity_unique_v2268`)으로 중복을 거른다.
- 새 달 첫 실행은 지난달에 끝까지 처리하지 못한 날짜만 따라잡는다(상태 키 `cron_recurring_state_v22976`). 지난달이 끝난 뒤 만든 규칙,
  지난달 지정일에 꺼져 있던 규칙은 넣지 않는다. 새 달에 규칙을 고치면 고치기 전 값으로 지난달 몫을 먼저 넣는다.
- 한 실행의 저장소 호출은 이 단계에서 30회로 묶는다(약 240개 규칙). 모의 실행: 가계부 32·42·102개 × 지정일 25·28·30일,
  10/1~12/31 매일 → 빠짐 0, 지연 0, 중복 0, 예약 실행 전체 최대 16·20·24회(고치기 전 32개·28일은 11월 10건·12월 15건 빠짐).
- **배포 때 주의:** 상태 키가 없는 첫 실행은 지난달을 끝까지 처리한 것으로 본다(배포하자마자 지난달 몫을 한꺼번에 넣지 않으려는 것).
  그래서 매월 1일 배포는 피한다. 이번 달 몫은 첫 실행이 지정일 날짜로 채운다.
- **실제 DB 확인 필요:** 픽스처는 PostgREST 의 `or`·`not.` 문법을 그대로 통과시켜 이 조회 문법을 검증하지 못한다. 쓰는 열
  (`is_active`, `last_applied_month`, `day_of_month`, `created_at`)은 기존 운영 조회(`fetchRecurring`)가 이미 읽는 열이다.
  틀리면 목록 조회가 매일 실패해 관제에 `scheduled_error` 로 드러난다(조용히 빠지지 않는다).

### O. 다시 확인했지만 결함이 아닌 것

  “buttonLayout을 vertical 로 설정하면 … 최대 5개까지 노출”이라고 적는다(`docs/kakao-manual/03_KAKAO_CANONICAL_RULES_AND_CONFLICTS.md` 49행).
  고치지 않는다. 실제 단톡방 화면 확인은 운영자 몫이다.
