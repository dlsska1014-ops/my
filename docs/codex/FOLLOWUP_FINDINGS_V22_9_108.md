## Gemini 결함 주장 ①~⑤ 대조

- **G-1** (P2) 상단 통합 검색(`api/user-api.js` handleUserTxSearch)이 가계부 전체 기간을 최대 40,000행까지 1,000행씩 순차로 읽어 JS 에서 부분문자열로 거른다(Gemini ①). **맞음.** 검색어를 낱말로 나누지 않고(`hay.includes(needle)`) 결과 50건 상한, DB 조건 없음(`fetchAdminRowsRange` 는 날짜·가계부·type 만), 요청당 DB 호출 예산 50(router.js `__AB_DB_BUDGET`) 안에서 최악 45~46회. 홈·기록 탭 필터(`my/mobile-home.js`)는 낱말 8개 AND·금액 완전 일치·보고 있는 달만이라 같은 검색어의 결과가 다르다. 예시 ‘신한카드 점심 → 0건’ 은 늘 그렇지는 않다(hay 가 `memo category payment_method raw_text spender_name` 순이라 결제수단 뒤에 원문이 ‘점심…’ 으로 이어지면 우연히 맞는다). 40,000행을 넘으면 422 too_many_rows, 재시도가 겹치면 예산 초과 500. CPU 10 ms 초과는 코드만으로 확정할 수 없다(측정 필요). 남음: 다음 판에서 상단 검색을 홈 필터와 같은 낱말 규칙으로 맞추고(디바운스 350 ms 그대로) 기간을 최근 12개월로 제한하거나 서버 `ilike` 조건을 붙인다. 지금 트래픽(기록 471행 규모)에서는 체감 문제가 아니다.
- **G-2** (P3) 웹 `#smartInput` 이 단건만 저장하고 카카오는 `parseMultipleTransactions` 로 다건을 저장하므로 ‘커피 4500, 택시 8000’ 이 웹에서 앞 금액만 저장되고 나머지가 메모에 섞인다(Gemini ②). **부분 맞음.** 저장 경로가 단건인 것(`handleAdminAddTransaction`·`handleMyAddTransaction` 모두 `createManualTransaction` 1회)과 칸 채우기(첫 금액 = 금액 칸, 첫 금액 토큰만 뺀 문장 = 메모)는 사실이다. 그러나 V22.9.93 Q-26 이후 금액이 둘 이상이면 저장 단추가 꺼지고 ‘금액이 둘 이상이에요. 여기서는 한 번에 한 건만 저장돼요. 한 건씩 나눠 적어 주세요’ 가 나온다(`client/shared-input-parsers.js` splitNeeded, 제출 preventDefault). 금액·메모 칸을 손으로 고쳐야만 풀린다. 안내 문구(placeholder·/quick-input-help)도 다건을 약속하지 않는다. 남은 불일치는 둘: (a) 메뉴 설명 ‘한 줄·여러 줄 입력 예시’(`web/menu-and-guides.js`)가 낡은 문구, (b) 서버는 다건 문장을 따로 거르지 않아 금액 칸을 고쳐 강행하면 섞인 메모로 1건 저장된다. 남음: (a) 문구 수정(다음 판), (b) 는 사용자가 금액을 직접 고친 뒤의 일이라 결함으로 보지 않는다.
- **G-3** (P2) `accountbook_settings` 에 JSON 을 통째로 읽고-고쳐-쓰는 키(수정 이력·식별 링크·방 연결·후원 집계)가 사용자 수에 비례해 커지고 가계부 잠금으로 직렬화된다(Gemini ③). **부분 맞음.** 실제로 사용자 수에 비례해 커지는 전역 단일 JSON 은 `user_identity_links`(가입·별칭 저장마다 전체 읽기·쓰기 + 전역 잠금 `settings-rmw:user_identity_links`, busy 면 12~30 ms 간격 3회)와 옛 `kakao_group_links` 거울(정본은 방별 행 `kakao_group_link_v2254:*`)이다. `transaction_edit_history` 는 코드 모양은 주장대로(거래당 20건, 맵 전체 upsert, 키 삭제 없음)지만 화면의 수정 폼이 전부 `/admin/update` 로 가고 그 핸들러는 이력을 쓰지 않아 실사용에서 거의 쌓이지 않고 읽는 곳도 없다(= 죽은 데이터). `support_stats:<날짜>` 는 날짜마다 한 줄이라 비대화가 아니고, 잠금 없는 읽기→더하기→upsert 라 동시 요청 하나가 빠질 수 있다(주석이 ‘대략’ 이라고 적음, V97 설계). 가계부 설정 잠금은 임대 90초·실패 즉시 `settings_rmw_busy`·재시도 없음. 남음: 출시 뒤 이용자가 늘면 `user_identity_links` 를 사용자별 행으로 나누는 것이 첫 순서(B-0 결정 2 의 별칭 예산과 함께). 지금 규모(사용자 77)에서는 문제 없다.
- **G-4** (P3) `computeCardUsageMap` 이 발급사 부분 일치로 카드를 고르고 동률이면 이름이 긴 카드에 몰아 실적을 왜곡한다(Gemini ④). **부분 맞음.** 매칭 규칙(`features/payment-methods-page.js`: 이름 일치·포함 또는 발급사 2자 이상 포함 + ‘카드’)과 동률 처리(`nm.length >= bestLen` 이라 길이 같으면 목록 뒤쪽 카드)는 주장대로이고, 어떻게 맞았는지와 무관하게 이름 길이만 비교하므로 **이름으로 정확히 맞은 카드가 발급사로만 맞은 더 긴 이름의 카드에 진다**(예: 결제수단 ‘신한카드 Mr.Life’ 가 같은 발급사의 ‘Deep Dream’ 으로). 영향은 /payment-methods 카드별 사용액과 /reports 카드 실적 목표(`my/reports-premium.js`)·미등록 카드 판정이다. 틀린 부분: `card-benefits.js` 는 이 함수를 쓰지 않고 자체 `cardMatchesRow` 로 고정 카탈로그 한 장만 계산하며 /card-benefits 는 기본값 404(두 스위치를 켜야 열림)라 운영에 노출되지 않는다. 남음: 이름 일치 > 이름 포함 > 발급사 일치 순으로 우선순위를 두고 동률은 목록 앞 카드로(검사 포함). 같은 발급사 카드가 두 장 이상인 가계부에서만 보이는 결함이라 출시 전 결함 수정 범위에 넣을 만하다.
- **G-5** (P3) 일반 사용자 화면의 폼이 `/admin/*` 로 전송되어 권한 경계가 흐리다(Gemini ⑤). **맞음(전송처)·결함 아님(보안).** 홈 빠른 입력·수정·삭제·날짜 시트 폼은 모두 `/admin/transactions`·`/admin/update`·`/admin/delete` 로 가고 `/my/transactions`·`/my/update`·`/my/delete` 로 보내는 폼·fetch 는 없다. 그러나 `/admin/*` 는 `resolveTransactionAccess` 가 관리자 세션 또는 사용자 세션 + 엄격한 역할 조회(owner·admin·member 만, viewer·pending·blocked 거절)로 판정하고, 수정·삭제는 기록이 속한 가계부 기준·구성원은 자기 기록만·‘기록만’ 정책·지출자 변경은 관리자만·같은 출처 검사(라우터 전역)까지 있다. 이름이 ‘admin’ 일 뿐 권한 범위는 설계대로라 보안 결함이 아니다.
- **G-6** (P3) `/my/*` 거래 경로가 화면에서 쓰이지 않은 채 더 약한 검사로 살아 있다(G-5 대조에서 찾음). `/my/update` 는 `orig_*` 기준값이 없어 칸별 충돌 감지·임대·재계획이 없고(J-9 의 ‘지출자 = 나’ 조건만), `/my/transactions` 에는 `/admin/transactions` 의 서버측 문장 검사(취소 내역·쉼표 소수·날짜 불일치·단위 없는 한 자리)와 실행 취소 표가 없다. 수정 이력(`transaction_edit_history`)은 `/my/update` 만 남긴다(G-3). 남음: 다음 판에서 `/my/*` 거래 경로를 `/admin/*` 핸들러로 묶거나 닫고, 수정 이력은 지우거나 `/admin/update` 로 옮긴다.
- **G-7** (P3) 상단 검색의 숫자 OR 오탐(G-1 대조에서 찾음). 검색어의 숫자를 모두 이어 붙인 뒤(`q.replace(/[^0-9]/g, "")`) 금액 문자열에 들어 있기만 하면 OR 로 맞춰 ‘점심 12000’ 이 메모와 무관한 12,000원·112,000원 거래를 모두 돌려주고, ‘커피 4500 택시 8000’ 은 ‘45008000’ 이 되어 숫자로는 못 찾는다. 기록 탭의 ‘이 페이지에서 빠른 검색’(#v8Search)은 화면 글자 단일 부분문자열이라 한 화면에 검색 규칙이 세 가지다. 남음: G-1 과 함께 홈 필터 규칙(낱말 AND·금액 완전 일치)으로 통일.
- **G-8** (P3) 단톡방 연결 목록이 조용히 비거나 잘릴 수 있다(G-3 대조에서 찾음). `fetchKakaoGroupLinkMap` 이 비엄격 읽기(`optionalSupabase`)라 DB 오류도 ‘아직 연결된 단톡방이 없어요’ 로 보이고, 방별 행을 `limit=5000` 단일 요청으로 읽어 페이지 처리가 없다(코드 자체 주석이 경고한 PostgREST max-rows 잘림과 같은 꼴). 같은 조회를 계정 통합과 가계부별 방 연결 정리도 쓴다. 지금 방 연결 수(수십)에서는 안 보인다. 남음: 읽기 실패는 오류 문구로, 5000 행 넘으면 페이지 처리(출시 뒤).

- **G-10** (P3) 홈이 14개 절로 길고 ‘얼마 썼나’ 가 세 곳에 서로 다른 정의로 나온다(Gemini UX ②). **부분 맞음 — 결함 아님.** 절 14개와 순서(설정 띠·상단바·예산 카드·한 줄 기록 줄·주간 스트립·챌린지·이번 달 리포트 4장·수입 대비 사용/들어온 돈/나간 돈·캘린더 링크·바로가기(접힘)·소비 흐름(접힘)·빠른 입력·정기 카드·최근 내역·후원 줄)는 주장대로이고 일부는 조건부·접힘이다. 그러나 ‘세 가지 정의’ 는 틀리다: 예산 카드 아랫줄의 ‘예산 쓴 돈’·‘예산 안 정한 지출’ 은 분류별 예산일 때만 나뉘고 더하면 ‘나간 돈’ 이다(전체 예산이면 같은 수, `domain/budgets.js` budgetedExpense·uncoveredExpense); 이번 달 리포트 4장에는 달 지출 합계가 없고(1위 분류·최근 7일·가장 높은 예산 항목·앞으로 나갈 돈) ‘N월 지출’ 카드는 V22.8.97 에 이미 뺐다. 홈 구성은 사용자 의견(V102:J-1·J-2 로 빠른 검색 칸 제거)으로 다듬어 왔고 출시 전 안정화 우선이라 더 줄이지 않는다. 줄이려면 사용자가 지목한다.
- **G-11** (P3) `#smartInput` 에서 Enter 가 저장하지 않고, 빠른 입력(#add)이 본문과 시트 두 벌이다(Gemini UX ③). **부분 맞음.** Enter 는 칸(금액·날짜·유형·메모·결제수단·분류)만 채우고 한 줄 칸을 비우며 저장은 ‘기록 저장’ 단추다 — V22.9.90 IME 조합 중 Enter 이중 저장을 막은 설계(주석 ‘조합 중 Enter 는 예전처럼 저장하지 않는다’)라 결함이 아니다. #add 는 두 벌이 아니라 한 노드다: 899px 이하에서는 본문에서 숨기고(`abQuickSheetOnly`) 시트로만 열며 앵커 이동·스크롤 고정을 처리한다. 남은 것 하나: 900px 이상에서 시트를 한 번 열면 노드가 오버레이로 옮겨지고 닫을 때 숨기기만 해 본문의 빠른 입력이 새로 고칠 때까지 사라진다(`v5-bundle-mains.js` close). 데스크톱에서 시트를 여는 단추가 보이는 경우에만 드러난다. 남음: 닫을 때 본문 자리로 되돌리기(다음 판, 작은 수정).
- **G-12** (P3) 구성원(member) 권한이 화면마다 달라 보이고 내비 표시가 서버 권한과 다르다(Gemini UX ④). **서버 기준 맞음 — 표시만 남음.** 쓰기 = owner·admin·member, 관리 = owner·admin, member 는 자기 기록만 수정·삭제(소유자가 ‘기록만’ 으로 두면 그것도 막힘), 결제수단·예산 저장·정기지출·분류 키워드·/my/settings·단톡방 연결·챌린지·정산·참여자 관리는 서버(`access-control.js` canManageMyHousehold 등)가 막는다(역할 표는 대조 보고에 있음). 그러나 공통 내비의 ‘관리자 전용’ 표시(`unified-nav.js` adminOnlyKeys)는 참여자·초대와 단톡방 연결 두 메뉴에만 붙어, 구성원은 설정·결제수단을 눌러 봐야 막힌 것을 안다. 남음: 메뉴 표시를 서버 권한과 같게(설정·결제수단·예산 저장에도 ‘관리자 전용’) 또는 구성원용 읽기 전용 화면(다음 판).
- **G-13** (P3) 내비가 두 벌(renderMySideNav·renderUnifiedNav)이고 `html-postprocess.js` 가 수백 줄 replace 로 응답을 고치며 `</option>` 을 지운다(Gemini UX ⑤). **부분 맞음 — 결함 아님.** 소스에는 두 함수가 있고 8곳(/my/settings·/my/groups·/my/backup·참여자·설정 안내·로그인한 /start-guide)이 옛 사이드바로 그리지만, 모든 HTML 응답이 `promoteLegacyUserLayoutToV5` 를 거쳐 옛 사이드바를 잘라 내고 공통 내비로 바꾸므로 사용자에게 가는 HTML 에는 내비 하나뿐이다. ‘수백 줄 replace’ 는 과장이다(`normalizeUserFacingUi` 227줄에 replace·replaceAll 74회, 대부분 제목·문구 조건). `</option>` 제거는 내용이 빈 option 의 끝 태그만 지우는 것으로 HTML 규칙상 생략 가능하고 홈 35 KiB 예산을 지키려는 조치다(V22.9.97). 정리(8곳을 공통 내비로 직접 그리기)는 출시 뒤 후보.
- **G-14** (P3) 거래 유형이 수입·지출뿐이라 적금·저축 이체와 카드대금이 지출로 집계되고 결제수단 잔액이 거래로 가감되지 않는다(Gemini 기능 공백 ①). **맞음.** `normalizeType` 은 income·expense·"" 셋만, 저장 단계도 둘로 접고, ‘적금·저축·투자 + 입금·이체·납입·송금’ 은 ‘저축/투자’ 지출로 통계에 들어간다. 이동(transfer) 유형도 거래별 ‘통계 제외’ 칸도 없고, 결제수단 잔액은 손으로 넣는 값이다(카드만 이번 달 거래 합을 보여 줌). 남음: 출시 뒤 결정 — ‘이동’ 유형(수입·지출 통계 제외, 잔액만 이동) 또는 거래별 통계 제외 칸. 스키마·리포트·카카오 해석이 함께 바뀌어 작은 일이 아니다.
- **G-15** (P3) 할부가 개월로 나뉘지 않고 ‘정산받음’ 이 수입이 되며 환불 연결은 환불만 다루고 기본 꺼짐이다(Gemini 기능 공백 ②). **부분 맞음.** 할부를 나누는 코드는 없어 한 건 전액이 적은 날짜에 잡힌다(맞음). ‘점심 정산받음 30000’ 은 `transactionTypeFromText` 의 받음 규칙으로 수입·‘환급’ 분류가 된다(결과는 맞고 경로 설명은 다름). 환불 연결(`REFUND_LINKS_ENABLED`, 기본 꺼짐)의 범위는 ‘환불만’ 이 아니라 ‘환급 분류 수입 ↔ 365일 안 원지출 연결’ 이고 연결하면 그 달 지출·분류·정산에서 뺀다(소유자·관리자만). ‘정산받’ 은 환급 낱말이라 플래그를 켜면 연결 대상이다. 1/N 정산(카카오 ‘더치페이·1/n 정산’, 정산 화면)은 있다. 남음: 플래그 켜기는 기존대로 별도 승인(DB 적용 포함), 할부 분할은 출시 뒤 결정.
- **G-16** (P3) 공유 시트(Web Share Target)로 들어오는 길이 안내에 없다(Gemini 기능 공백 ③). **맞음.** 매니페스트 `share_target`(GET /app, share_title·share_text·share_url)이 있고 공유된 글은 한 줄 입력 칸에 채워져 곧바로 해석되며 저장은 사용자가 누른다(URL 은 붙이지 않음, 200자). 그러나 공개 시작가이드·로그인 시작가이드 8단계·/quick-input-help 어디에도 공유 시트·홈 화면 추가 안내가 없다. 남음: 안내 한 줄(문구만, 다음 판).

## Gemini 수익화 전략(3단계) 대조 — Claude 판단

- **G-17** (P3) Gemini 는 ① 문맥 제휴(CPA/CPS) 먼저 → ② 방 단위 소액 이용권 → ③ 계산표 + 애드센스 순서를 제안했다. **판단: 순서가 이 프로젝트의 지금 상태와 반대다.** 근거와 권고:
  - ③ 계산표 + 애드센스는 이미 만들어져 있다(V106 계산표 6개·V107 광고 게이트·이 판의 허용 목록 53쪽). 재검토 요청만 남았고(V107:D-17) 이용자에게 마찰이 없다. **1순위 그대로.** 승인 뒤 `ADS_MODE=live` 변수 추가는 사용자 지목.
  - ① 문맥 제휴는 11-03 조사(`review-artifacts/monetization-2026-11-02/AFFILIATE-RESEARCH.md`)대로 애드픽·텐핑 공개 목록에 알뜰폰·연금·ISA 캠페인이 없고, 가입 주체는 사업자(일반과세)로 결정됐다. 가계부 데이터로 금융상품을 골라 보여 주는 개인화 추천에 성과 수수료를 붙이면 금소법 ‘중개’ 로 볼 여지가 있어(조사 §금소법) 글 안의 고정 링크만 가능하다. 애드센스 재검토 결과가 나오기 전에 글 6편에 제휴 유도 문구를 넣으면 ‘가치가 별로 없는 콘텐츠’ 판정 근거가 늘 수 있다. **2순위: 애드센스 판정 뒤, 맞는 캠페인이 실제로 있을 때만**(지금은 없음), 세무·통신비 글의 고정 링크부터.
  - ② 방 단위 소액 이용권은 사용자가 이미 접은 구조(10-27 ‘방당 유료·토스페이먼츠 접음’, 11-05 ‘유료 전환은 사용자 추이 뒤’ — 일 방문 10~100명·수익 0)이고, 11-04 결정 ‘기능은 후원과 무관’ 과도 어긋난다. PG 계약·환불·세금계산서·결제 화면이 필요해 출시(11-13) 전 결함 수정 범위를 넘는다. **지금 하지 않는다.** 출시 뒤 관제 이용 현황(방 수·활성 가계부·월 기록 수)이 쌓이면 11-01 권고대로 연간 패스부터 다시 본다.
  - 결론: 애드센스(승인 → live) → 후원(운영 중, 오픈채팅 안내) → 제휴 고정 링크(캠페인이 생기면) → 연간 패스(지표 뒤). 사용자가 ‘너의 판단을 기준’ 이라고 했으므로 이 순서를 기본으로 두고, 바꾸려면 그때 지목한다.
