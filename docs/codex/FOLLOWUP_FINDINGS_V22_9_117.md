# V22.9.117 계정 잇기 확인 화면 (2026-11-10)

사용자(2026-11-10 오후)가 로그아웃한 뒤 구글 검색으로 들어와 웹에서 카카오로 로그인하자, 계정 잇기 확인 화면(/my/account-link)이 나왔다. ‘카카오로 확인하고 잇기’ 를 누르면 늘 ‘확인한 카카오 계정이 이 가계부의 카카오 계정과 달라요’ 가 떴다. 사용자는 화면 배치도 엉망이라고 했다("로그아웃하고 구글에서 검색해서 들어가려면 … 이렇게 나오는데 왜그러는거야 ui 배치도 좀 엉망이고").

원인은 운영 DB 덤프(2026-11-10 13:44 KST, 저장소 밖)로 확인했다. 카카오 id·이름·키 원문은 보지 않고 해시가 같은지만 대조했다.
- 잇기 제안은 1건이다. 웹 계정(가계부 6개·기록 72건)과 카카오톡 방 기록 계정(가계부 2개·기록 62건)을 잇자는 제안이고, 2026-11-08 방 기록에서 생겼다.
- 그 웹 계정에는 카카오 로그인이 둘 있다. 둘 다 2026-07-05 웹 카카오 로그인으로 생겼고, 2026-07-13 관리자 통합으로 한 계정에 모였다.
  - 첫째(06:48Z)는 강한 식별(provider kakao)이다.
  - 둘째(08:37Z)는 링크 표의 `kakao_login:<id>` 별칭이다.
- 제안의 카카오 해시는 둘째 것이다. 카카오톡 방이 보낸 appUserId 가 그것이다.
- 지금 브라우저는 첫째 카카오 계정으로 로그인돼 있다. 휴대폰 카카오톡과 PC 브라우저의 카카오 계정이 서로 다른 것으로 보인다.
- 앱이 엇갈렸을 가능성은 낮다. 둘째 id 는 과거 웹 로그인 id 와 같다. 그러니 봇에 연결된 앱이 웹 로그인 앱이라는 V77:N-7 의 전제가 맞다.

- **L-1** (P2) 확인 단계(V22.9.91)는 방금 확인한 카카오 id 가 제안의 카카오 id 와 꼭 같아야 했다. 그래서 카카오 로그인이 둘 이상 붙은 웹 계정은 다른 카카오 로그인으로 확인하면 늘 ‘다른 카카오 계정’ 이었다.
  - 로그인 콜백에서도 조용히 실패했다. 그 뒤 /my 를 열 때마다 확인 화면으로 돌아왔다. ‘나중에 하기’ 를 누르면 7일 동안은 안 나왔다.
  - 고침(`auth/kakao-account-link.js` kakaoAccountLinkProofAfterKakao·kakaoAccountLinkOtherLoginTrustedV229117): 확인 화면에서 ‘카카오로 확인하고 잇기’ 를 누른 뒤에만, 세 가지를 그 자리에서 다시 읽어 모두 맞으면 받는다. 로그인 콜백만으로는 잇지 않는다(L-7).
    - 방금 확인한 카카오 id 의 주인이 제안의 웹 계정이다. 주인을 찾는 순서는 로그인과 같다(lookupKakaoLoginOwner, 합친 계정은 따라감).
    - 방금 확인한 카카오 id 와 제안의 카카오 id 가 둘 다 그 웹 계정의 믿는 카카오 로그인이다. 믿는 카카오 로그인은 강한 식별과, 옛 웹 카카오 로그인이 링크 표에 쓴 `kakao_login:<id>` 별칭(provider kakao_login)뿐이다(L-5·L-6).
    - 제안의 카카오 id 의 주인이 아직 그 웹 계정이다.
  - 운영자 계정은 두 카카오 id 모두 옛 웹 로그인 별칭(provider kakao_login)이 웹 계정을 직접 가리킨다(덤프로 확인). 그래서 첫째 카카오 계정으로 확인해도 받는다.
  - 합치기 표의 h 는 제안의 해시이고, c 는 제안의 방 기록 계정이다(L-8).
  - 다른 사람의 카카오 계정, 어느 계정에도 없는 카카오 계정, 주인이 바뀐 제안 id, 믿지 않는 별칭이나 사용자 키로만 이어진 id 는 거절하고 제안은 남긴다. 그때는 다시 확인 단추로 제안의 카카오 계정에 직접 로그인하면 잇는다(예전 규칙).
  - 남의 세션 쿠키만으로는 여전히 못 잇는다. 방금 한 카카오 확인이 있어야 한다.
  - 운영 확인: 배포 뒤 사용자가 PC 보통 브라우저에서 첫째 카카오 계정으로 로그인하면 /my 가 확인 화면을 보인다. ‘카카오로 확인하고 잇기’ 를 누르면 잇는다. 잇기는 되돌릴 수 없고, 주 계정은 방 기록 계정이다.
- **L-2** (P3) 확인 화면 배치가 휴대폰 폭에서 흐트러졌다. 390px 화면을 헤드리스 Chrome 모바일 흉내로 찍었다.

  - 고침: 이 화면 전용 CSS(KAKAO_ACCOUNT_LINK_PAGE_CSS)와 테마 스크립트를 넣었다. 오류는 제목 바로 아래로 옮겼다. 두 계정 줄은 이름과 숫자를 두 줄로 나눴다.

## 독립 보안 검토와 재시험 (2026-11-10 저녁)

PR 전에 독립 보안 검토를 한 번 받았다. 검토자는 저장소를 바꾸지 않고 오프라인 재현만 했다. 검토가 짚은 것을 고친 뒤, Claude 가 위조 요청의 모양을 넓혀 다시 시험했고 길 두 개를 더 찾아 막았다.
위조 요청이 통하려면 확인 모드(observe)이거나 Secret 이 새야 한다. 운영은 enforce 다(/ready 의 skill_caller_auth.mode).

- **L-5** (P2) 초안은 다른 카카오 로그인으로 확인할 때 링크 표의 `kakao_login:` 별칭을 provider 와 상관없이 믿었다. 단톡방 요청이 쓰는 별칭(provider skill)도 믿었다.
  - 위조 요청으로 남의 카카오 id 를 자기 채팅 계정 별칭으로 심을 수 있다. 그러면 피해자의 다음 방 기록이 공격자 계정 앞으로 잇기 제안을 만든다. 공격자가 자기 카카오로 웹에서 확인하면 피해자의 방 기록 계정을 이었다. 공격자 계정이 비어 있으면 로그인만으로 이었다.
  - 찾은 곳: 독립 보안 검토. 초안에만 있었다. 운영 V22.9.116 은 제안의 카카오 계정으로 직접 로그인해야 해서 해당 없다(검사 7번을 운영 번들에 돌려도 합치지 않는다).
  - 고침: provider skill 별칭은 믿지 않는다(L-6 에서 더 좁혔다). 검사 7번.
- **L-6** (P2) L-5 를 고친 첫 판도 사용자 키(users.kakao_user_key)와 provider identity_merge 별칭을 믿었다. 둘 다 위조로 만들 수 있었다.
  - Secret 이 새면 위조 요청이 웹 로그인 사용자 키와 같은 꼴의 봇 키로 새 채팅 계정을 만들 수 있다(L-10). 그 사용자 키를 믿으면 L-5 와 같은 공격이 된다(검사 9번).
  - 그 계정을 공격자 자기 웹 계정과 V22.9.91 잇기로 합치면, 합치기 함수(관리자 통합과 같은 함수)가 그 사용자 키를 identity_merge 별칭으로 남긴다. 그 별칭을 믿어도 같은 공격이 된다(검사 9b).
  - 찾은 곳: 보안 검토를 반영한 뒤 Claude 재시험.
  - 고침(kakaoAccountLinkOtherLoginTrustedV229117): 믿는 카카오 로그인은 그 웹 계정의 강한 식별과 provider kakao_login 별칭뿐이다. provider kakao_login 별칭은 옛 웹 카카오 로그인만 썼고 지금 코드는 쓰지 않는다.
  - 방금 확인한 카카오 id 와 제안의 카카오 id 가 둘 다 믿는 카카오 로그인이어야 한다. 한 계정의 강한 식별은 하나뿐이다. 그래서 피해자가 웹에서 위조 계정으로 로그인해 강한 식별을 그쪽에 남겨도, 두 id 를 다 믿는 자리에 둘 수 없다(검사 9번 둘째 확인).
  - 관리자 통합만으로 붙은 카카오 로그인은 이 길로 받지 않는다. 확인 화면의 다시 확인 단추로 그 카카오 계정에 직접 로그인하면 잇는다(검사 10번). 운영자 계정은 두 별칭 모두 provider kakao_login 이라 받는다.
- **L-7** (P3) 초안은 다른 카카오 로그인이어도 한쪽이 비어 있으면 로그인 콜백만으로 말없이 이었다. 한 웹 계정을 두 사람이 쓰면(관리자 통합, 가족이 함께 쓰는 계정) 한 사람이 다른 사람의 방 기록 계정을 확인 없이 이을 수 있었다.
  - 찾은 곳: 독립 보안 검토.
  - 고침: 다른 카카오 로그인이면 로그인 콜백은 합치기 표를 주지 않는다. /my 가 확인 화면을 보이고, 단추를 누른 뒤에만 잇는다(검사 1·4번).
- **L-8** (P3) 합치기 표(5분)가 제안의 방 기록 계정을 묶지 않았다. 확인한 뒤 5분 안에 같은 카카오 id 의 다른 방 기록 계정이 제안을 바꾸면 그 계정을 이었다. V22.9.91 부터 있던 틈이다.
  - 찾은 곳: 독립 보안 검토.
  - 고침: 표에 방 기록 계정(c)을 넣고, 합치기 단계에서 제안의 방 기록 계정이 같은지 본다(검사 8번).
- **L-9** (P3) 제안의 카카오 id 가 이 웹 계정을 떠났을 때도 ‘확인한 카카오 계정은 이 웹 계정에 연결된 카카오 계정이 아니에요’ 가 나왔다. 틀린 말이다. 카카오톡 인앱 브라우저에서는 안내도 단추도 없이 같은 말만 되풀이됐다.
  - 찾은 곳: 독립 보안 검토.
  - 고침: 그 경우는 kakao_offer_unverified 로 알린다(‘이 잇기 제안의 카카오 계정이 이 웹 계정에 연결돼 있는지 확인하지 못했어요. …’).
  - 인앱에서는 ‘카카오톡 안에서는 카카오 계정을 바꿀 수 없어요. 인터넷 브라우저(크롬·사파리 등)로 다시 들어와 …’ 한 줄을 붙인다(검사 2·3·5번).
- **L-10** (P2, 남음) 단톡방 요청의 봇 키 모양을 검사하지 않는다. 웹 카카오 로그인 사용자의 내부 사용자 키는 카카오 id 로 만들 수 있는 꼴이다.
  - 확인 모드(observe)나 Secret 유출 때, 그 꼴의 봇 키를 단 위조 요청은 그 웹 계정처럼 봇을 쓴다. 오프라인 재현에서 위조 요청이 그 웹 계정의 가계부 목록을 받았다.

  - V22.9.117 전부터 있던 문제다. 운영은 enforce 라 Secret 없는 요청은 403 이다.
  - 고침 후보(다음 결함 수정 판): 봇 키가 내부 키 꼴(`kakao_login:`·`local_web:`·`merged:` 등)이면 받지 않는다. 등록 검사 여럿이 픽스처 웹 사용자의 키를 봇 키로 쓰므로 함께 고친다.

  - 링크 표 별칭이 합치기 뒤 정리를 건너뛰어 없어진 계정을 아직 가리키면, 믿는 카카오 로그인으로 세지 않는다.
