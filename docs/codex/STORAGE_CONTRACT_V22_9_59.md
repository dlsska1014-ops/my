# V22.9.59 저장·복구·삭제 계약

메모는 PostgreSQL 문자 단위로 160자, 결제수단은 40자까지 허용합니다. JavaScript UTF-16 단위와 구분하여 Unicode 코드 포인트를 셉니다. 조합 문자는 각각 한 문자로 세며, NUL과 단독 surrogate는 저장 후보에서 거절합니다. 파서가 확정한 두 필드의 값을 조용히 자르지 않습니다. 입력 파일과 현재 문서의 원문은 유지하고 초과 행의 제외 사유에 실제 한도를 안내합니다. 원문 미리보기와 기존 raw_text 길이 정책은 완전 백업 복원을 제공하지 않습니다.

동일한 검사를 미리보기와 저장 직전 정리에 사용하며, 서명·고정 ID·전송·재조회 해시에는 허용된 원래 값을 사용합니다. 정상 RPC 응답도 실제 행의 전체 저장 필드와 ID를 대조합니다. 응답 건수만 맞거나 HTTP 200이더라도 값이 다르거나 조회할 수 없으면 확인 필요로 표시하고 pending을 유지합니다. 저장 뒤 발생한 조회 오류를 저장 전의 확정 거절로 오인하지 않습니다. 이미 대조한 신규 묶음을 다시 조회하지 않아 기존 1,000행 묶음과 연속 저장 한도를 유지합니다.

구형 토큰의 초과값을 자르거나 같은 서명에 다른 ID를 부여하지 않습니다. 구형 pending의 초과값은 원래 상태를 그대로 두고 추가 RPC를 거절합니다. 만료·소실 토큰과 정확한 값이 확인되지 않는 pending은 자동 해제하지 않습니다. 파일을 변경한 별도 원본까지 같은 작업으로 판정하는 기능이나 완전 백업 복원은 포함하지 않습니다.

새 소속 표식은 `my_import_scope_v22959:SHA256(householdId):sourceHash` 키에 v·household_id·source_hash·state_key만 기록합니다. 원문은 기록하지 않습니다. 본 상태 키는 기존 `my_import_source_v22955:SHA256(householdId|sourceHash)`를 유지합니다. 표식을 먼저 기록하고 본 상태와 RPC를 준비하므로, 부분 실패 후에도 본 상태의 가계부 소속을 확인할 수 있습니다. 유효한 서명과 원본 해시를 가진 구형 토큰은 같은 키의 표식만 추가할 수 있으며, 구형 pending의 원래 바이트는 바꾸지 않습니다.

가계부 삭제는 같은 `transaction-import:<householdId>` 잠금으로 가져오기와 직렬화합니다. 선택한 가계부의 표식만 완전 조회하며 상한을 넘거나 형식·소속을 확인할 수 없으면 삭제를 중단합니다. 해당 가계부에 미확정 pending이 있으면 관계형 purge RPC를 호출하지 않습니다. 정확한 기존 저장값으로 확인된 pending만 논리적으로 완료로 판정합니다. 다른 가계부의 pending은 삭제를 막거나 정리하지 않습니다. 본 상태는 읽었던 전체 값으로 조건부 삭제한 뒤 표식을 마지막으로 삭제합니다. 정리 실패는 `importCleanupPending`과 `household_import_cleanup_pending` 관측으로 관계형 삭제 성공과 구분하며, 표식은 후속 명시적 정리를 위해 남습니다.

소속 표식이 없고 검증 가능한 원본·유효한 토큰도 없는 과거 해시 키의 가계부는 추측하지 않습니다. 이러한 구형 상태는 삭제 후에도 남을 수 있으며 이번 작업에서 자동 정리하거나 이관하지 않습니다. 표식만 남은 부분 실패는 삭제 시 해당 가계부의 표식만 정리할 수 있습니다. 본 상태 기록의 결과 자체가 불명확하여 pending이 남은 경우에도 거래가 없다는 이유만으로 보호를 해제하지 않습니다.

복구 후보는 같은 실제 소스에서 별도 파일로 생성하고, 빌드 상수 `MY_IMPORT_WRITES_ENABLED_V22959=false`로 `/my/import`의 저장, 관리자 JSON 가져오기, 최종 확인 및 적용 POST를 거절합니다. 열 연결 상태를 새로 만드는 요청도 거절합니다. 이미 열린 탭·같은 토큰·만료 또는 소실 토큰의 재전송으로 새 ID를 쓰지 않습니다. 교체 전에 전달된 요청의 실행을 취소하는 기능은 없으므로 원래 지연 요청이 원래 ID로 끝나는 경우와 복구 후보가 새 RPC를 보내지 않는 경우를 구분해 검증합니다. V44로 단순 복귀하지 않습니다.

Worker 임대와 조건부 settings 정리는 DB 트랜잭션 하나가 아닙니다. 혼합된 구형 Worker의 이미 실행 중인 요청, 임대 만료 경계와 관계형 purge의 원자적 순서까지 운영에서 보장하려면 추가 DB 계약이 필요합니다. 최소 제안은 import와 purge가 같은 가계부 advisory transaction lock을 먼저 획득한 뒤 존재·구성원 자격을 다시 확인하고, 소속이 확인된 상태와 관계형 삭제를 같은 트랜잭션에서 처리하도록 하는 것입니다. 소속은 `household_id uuid REFERENCES households(id) ON DELETE CASCADE`, `source_hash` 및 유일한 state_key로 확인할 수 있는 등록 관계로 관리하고 원문은 추가하지 않습니다. 상태 생성·리비전 변경과 등록도 원자적으로 처리해야 합니다. 이 테이블·RPC 확장은 설계 검토 사항이며 SQL을 작성하거나 실행하지 않았습니다. 구형 소속 불명 상태는 검증 자료가 확보될 때만 등록할 수 있습니다.

정리 실패 후 이미 삭제된 가계부의 표식을 자동으로 반복 삭제하는 외부 작업은 구현하지 않았습니다. 별도 승인하에 가계부 부재, 표식의 해시·소속, 본 상태의 정확한 revision과 pending 여부를 재확인하고 동일한 조건부 정리를 수행해야 합니다. 운영 승격, 실제 복구 승격, CPU·exact-count 비용과 실기기 검증도 남아 있습니다.
