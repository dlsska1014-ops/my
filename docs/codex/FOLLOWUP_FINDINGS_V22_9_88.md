# V22.9.88 Codex 검토에서 찾은 항목

V22.9.81~87 을 운영에 낸 날(2026-10-29) Codex 가 운영 소스(main 7857cd5)를 검토해 여섯 가지를 짚었다. 사용자가 그 목록을 Claude 에게 넘겨 확인과 고침을 맡겼다.
이 문서는 발견 기록만 둔다. 상태·고친 판·검사는 `docs/codex/FINDINGS_LEDGER.md` 의 `V88:` 행에서 추적한다. 파일 줄 번호는 7857cd5 기준이다.
- 여섯 항목 모두 Claude 가 코드에서 확인했다. 검사 `validation/validate-codex-findings-v22988.mjs` 는 7857cd5 코드에서 여섯 항목 모두 실패하고 이 판에서 통과한다.
- Y-6 은 V79:T-7 의 남은 틈과 같은 결함이다. 둘 다 이 판에서 닫는다.
- Y-2 는 운영 DB 함수가 있어야 닫힌다. 새 SQL 은 검토 전용(실행 금지)이라 적용 전에는 V22.9.87 과 같게 동작한다(‘일부 고침’).

## 항목
- **Y-1** (P2, 카카오 저장) 저장 전 실패가 남긴 저장 표식이 다음의 다른 문장을 계속 막는다(`kakao/transaction-save.js:274`).
  - 중복 조회나 최종 표식 쓰기처럼 거래를 보내기 전에 실패해도 처음 표식이 남았다. 그 뒤 다른 문장은 ‘저장 확인이 지연되고 있어요 … 같은 내용을 다시 보내지 말고 기다려 주세요’로 거절됐다.
  - 같은 문장을 다시 보내야 풀렸다. 날짜 말(‘어제’)이 다음 날 다른 날짜가 되거나 선택 가계부가 바뀌면 지문이 달라져 그것도 어렵다.
  - 고침: 보내기 전 실패는 이 요청이 쓴 표식을 지우고 ‘저장하지 못했어요’로 안내한다. 같은 문장의 재시도(앞 시도의 전송 결과를 모름)는 표식을 남겨 같은 번호로 잇는다.
  - 고침(덧붙임): 결과를 모르는 앞 표식은 10분까지만 다른 문장을 막는다. 막을 때는 ‘이번 내용은 저장하지 않았으니 잠시 뒤 다시’라고 알린다.
    10분이 지나면 늦게 들어올 전송은 없다고 보고 표식을 버린다(운영 이벤트 kakao_pending_write_expired, 행 수만). 별도 구매도 같은 기한이다.
- **Y-2** (P2, 실행 취소) 실행 취소가 그사이 다른 사람이 고친 기록을 지울 수 있다(`my/transactions.js:284`).
  - 앱이 읽어 지문을 견준 뒤 따로 지웠다. 예전 삭제 함수(accountbook_delete_transaction_v227)는 내용을 견주지 않아, 견준 뒤 지우기 전에 고친 기록도 지워졌다.
  - 고침: 새 DB 함수 accountbook_delete_transaction_if_v22988 이 행을 잠근(FOR UPDATE) 뒤 실행 취소 표 지문과 같은 일곱 칸을 다시 견준다. 같을 때만 v227 과 같은 감사 기록을 남기고 지운다.
    다르면 지우지 않고 undo_changed 로 돌아간다.
  - SQL 은 `migrations/V22_9_88_UNDO_DELETE_IF_UNCHANGED_APPLY_REVIEW_ONLY.sql`(실행 금지, 따로 승인)이다. 함수가 아직 없으면(PGRST202) 앱은 예전처럼 v227 로 지운다.
- **Y-3** (P2, 계정) 비밀번호를 바꿨는데 ‘저장하지 못했습니다’라고 할 수 있다(`auth/local-login-pages.js:260`).
  - 비밀번호를 바꾸면 예전 로그인이 모두 끊긴다. 그 뒤 새 로그인을 만들다 실패해도 409 ‘저장하지 못했습니다’였다. 변경 응답을 잃은 경우도 같았다.
  - 고침: 새 로그인만 실패하면 200 ‘바꿨습니다 … 새 비밀번호로 다시 로그인해 주세요’를 보이고 끊긴 로그인 쿠키를 지운다.
    결과를 모르면 503 ‘결과를 확인하지 못했습니다. 이미 바뀌었을 수 있어요’와 확인 방법을 보인다. 저장소가 분명히 거절하면 예전처럼 409 다.
- **Y-4** (P3, 카카오 저장) 여러 건 입력의 중복 안내가 다른 거래의 문장을 보인다(`kakao/transaction-save.js:133`).
  - 결과가 중복부터 돌아오는데 안내는 입력 순서의 첫 문장을 썼다. ‘새점심 / 중복원본’이면 ‘별도 구매 추가 새점심 …’으로 안내했다.
  - 고침: 결과를 입력 순서로 돌려주고, 중복 행에 그 입력 문장을 붙여 안내에 쓴다.
- **Y-5** (P3, 관리자 API) 관리자 API 로 메모·결제수단을 지울 수 없다(`api/admin-api.js:138`).
  - 부분 수정이 빈 문자열을 뺐다. 출처 기본값(source)이 늘 끼어 ‘변경할 내용이 없습니다’(empty_patch)도 나오지 않고, 아무것도 안 바꾼 수정과 감사 기록이 남았다.
  - 고침: 메모(memo·description)와 결제수단(payment_method·method)은 키가 있으면 빈 값·null 을 지우기로 넘긴다. 보내지 않은 키는 그대로 둔다.
    분류의 빈 값은 예전처럼 바꾸지 않는다. 부분 수정에는 출처를 넣지 않는다. 단건과 일괄 수정이 같다.
- **Y-6** (P3, 예약 실행) 리포트 다시 만들기 대기의 동시 갱신 틈(V79:T-7 의 남은 틈, `cron/recurring-auto-apply.js:731`).
  - 실행 끝 저장·?month= 경로·실행 밖 대기 보태기가 모두 다시 읽고 덮어썼다. 다시 읽은 뒤 저장 사이에 보탠 항목이 사라질 수 있었다.
  - 고침: 상태 값 맨 앞에 판 번호(rev)를 둔다. 세 경로 모두 읽은 판 번호가 그대로일 때만 쓴다(조건부 PATCH, 행이 없으면 없을 때만 넣기).
    밀리면 다시 읽어 합치고 세 번까지 다시 쓴다. 겹치지 않으면 읽기·쓰기가 한 번씩이라 예전보다 읽기가 한 번 줄었다.
  - V22.9.87 이하 코드는 판 번호 칸을 무시하고 읽는다. 그래서 되돌려도 상태를 읽을 수 있고, 다시 올리면 판 번호 없는 값을 판 번호 1로 바꾼다.
