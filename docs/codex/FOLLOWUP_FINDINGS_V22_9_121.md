# V22.9.121 후원자 식별 (2026-11-13)

사용자가 2026-11-13 아침 `/support` 의 ‘후원자에게 드리는 것’(배지·포인트 색 3가지·후원자 명단)을 붙여 넣고 “이거랑 후원자 식별 관련해서도 점검해야할 것 같아” 라고 했다.
운영 V22.9.120 코드(origin/main cafa226)를 읽어 점검했다. 약속한 세 가지는 동작한다(기존 검사 validate-v22995-support·validate-v22997-support 가 덮는다).
- 배지: 홈 가계부 이름 옆, 전체 메뉴, 참여자 화면에 보인다.
- 포인트 색 3가지(코랄·민트·라벤더): 후원자에게만 선택지가 나오고, 끝나는 날이 지나면 저절로 꺼진다.
- 공개 명단: 관리자가 명단 이름을 넣은 사람만 먼저 후원한 순서로 나온다.

빈틈은 넷(S-1~S-4)이고, 2026-11-04 에 정한 후원자 혜택 가운데 아직 만들지 않은 것이 하나(S-5)다.
사용자는 같은 날 Claude 의 질문에 ‘추천 범위’ 를 골랐다. 이 판은 S-1~S-4 를 고치고, S-5 는 출시 뒤 후보로 남긴다.
계정 잇기를 진단하다 본 것 하나(I-1)도 여기에 적는다(고치지 않음).

## 고친 것

### S-1 후원자가 어느 계정인지 알 길이 없음 (P2, 고침)
- 무엇: `/support` 는 후원 뒤 ‘말해가계부 로그인 이름’ 을 알려 달라고 했다. 하지만 카카오 로그인만 쓰는 대부분의 사용자에게는 로그인 이름이 없다. 사용자 화면에는 사용자 id 가 없다(V22.4.1 규칙).
  관리자 화면(`/admin/supporters`)은 user_id·로그인 이름·표시 이름(같은 이름이 하나뿐일 때만)으로만 찾았다. 그래서 운영자가 송금한 분의 계정을 찾을 수 없었다.
- 2026-11-04 사용자 결정 C-④(“누구든 내 계정 보안 탭에서 나의 고유 아이디 혹은 로그인 아이디를 확인할 수 있고, 그걸 나한테 알려주면 내 관리자 화면에는 리스트가 있어서 적용”)가 코드에 없었다.
- 고침:
  - 회원 번호 `MB-XXXX-XXXX` 를 더했다(`src/modules/my/member-code.js`). 사용자 세션에 서명하는 기존 비밀값으로 HMAC-SHA256 을 만들고, 앞 40비트를 크록퍼드 base32 8글자로 보인다. 새 변수는 없다. 로그인에는 쓰이지 않고, 번호에서 사용자 id 를 알 수 없다.
  - ‘내 계정·보안’(`/my/backup-login`) 맨 위에 회원 번호 카드와 복사 단추를 두었다. 안내는 ‘후원 확인이나 문의 때 운영자에게 알려 주는 번호예요. 로그인에는 쓰이지 않아요.’ 다.
  - 관리자 찾기에 ‘회원 번호’ 를 더했다. 기억 줄 `member_code:<번호>` 를 먼저 보고, 다시 계산해 같을 때만 믿는다. 없으면 최근 가입 500명을 훑는다.
  - 관리자 화면에 ‘전체 사용자 목록’ 을 더했다. 찾기 칸 하나(표시 이름·회원 번호·user_id 앞자리), 한 쪽 50명, 열은 회원 번호·표시 이름·계정 유형·가입일·user_id 앞 8자·후원 상태, 그리고 ‘후원자 추가’ 단추다. 화면 한 번에 DB 호출은 5회 이하다.
  - 기억 줄은 화면 GET 에서 쓰지 않는다. 내 계정·보안 화면이 실제로 보일 때 그 화면이 보내는 신호 `POST /my/member-code/seen`(늘 204, 세션 사용자 자신의 번호만, 없을 때만 넣기)이 쓴다. 미리 렌더링 규칙과 ‘GET 무변경’ 약속(validate-speculation-rules-v2297) 때문이다.
  - `/support` 의 후원 확인 문구를 ‘로그인 이름’ 에서 ‘회원 번호(웹 가계부 ‘전체 메뉴 → 내 계정·보안’)’ 로 바꿨다. 오픈채팅 안내에도 회원 번호 한 문장을 더했다.
- 독립 검토 1차 뒤 고친 것:
  - 기억 줄 값은 `{ user_id }` 만 적는다. 처음 본 시각은 남기지 않는다(방침 6절과 맞춤).
  - 머리(MB) 없이 쓴 ‘네 글자 네 글자’ 꼴은 줄표 계열 구분 기호(- _ . 와 여러 줄표)일 때만 번호로 본다. ‘Kate Moss’ 처럼 공백으로 띄운 이름은 이름으로 찾는다.
  - 내 계정·보안 저장이 오류로 같은 화면을 다시 그릴 때도 맨 위 회원 번호 카드를 둔다.
- 독립 검토 2차 뒤 고친 것:
  - 번호 꼴인데 번호로 읽히지 않는 말(‘MBTI ENFP 좋아’ 처럼 MB 로 시작하는 10글자 이름, 틀린 글자 U 가 든 번호)은 표시 이름으로 찾고 ‘회원 번호로 읽히지 않아 표시 이름으로 찾았어요’ 안내를 한 줄 붙인다. 전에는 안내만 보이고 목록을 읽지 않았다.
  - 마지막 쪽 뒤의 빈 쪽은 ‘이 쪽에는 사용자가 없어요’ 와 첫 쪽 링크를 보인다(전에는 ‘찾는 사용자가 없어요’).
  - 이름 찾기 와일드카드는 PostgREST 의 `*` 별칭 대신 SQL `%` 를 그대로 보낸다. 논리식의 큰따옴표 안에서도 `*` 가 바뀌는지 공식 문서로 확인되지 않았기 때문이다.
- 남음: 최근 가입 500명 밖에 있고 기억 줄도 없는 사용자는 번호 찾기에서 빠진다. 그런 사용자는 목록의 이름·id 앞자리 찾기로 찾는다(2026-11 사용자 수 ~100 이라 해당 없음).
- 검사: `validation/validate-supporter-id-v229121.mjs`.

### S-2 계정을 합치면 후원자 표시와 안내 확인 기록이 따라가지 않음 (P2, 고침)
- 무엇: 관리자 통합(`/admin/identity/merge`)과 계정 잇기(`/my/account-link/run`)는 모두 `performIdentityMerge` → 합치기 RPC(`accountbook_merge_users_v227`)를 거친다. 이 RPC 는 가계부 참여·기록·정기 규칙·로그인 연결은 옮기지만, 설정 표의 사용자 줄 `supporter:<id>`·`consent:<id>` 는 옮기지 않는다(저장소 정의 `schema_v22_7_0_auth_atomicity.sql`).
  - 웹 계정에 후원자 표시를 켠 사람이 단톡방 기록 계정과 이으면 배지·포인트 색·공개 명단 줄이 빠졌다(잇기의 주 계정은 단톡방 기록 계정).
  - 주 계정에 안내 확인 기록이 없으면 약관 안내 띠가 다시 떴다.
- 고침: 합치기 RPC 가 끝난 뒤 `carryUserSettingsAfterMergeV229121`(`src/modules/my/merge-carry.js`)가 네 줄을 한 번에 읽는다.
  - 보조 계정의 후원자 표시는 주 계정에 옮긴다. 둘 다 있으면 시작일은 이른 날, 끝나는 날은 한쪽이라도 없으면 없음, 메모·명단 이름은 주 계정 것 우선으로 합친다. 그다음 보조 줄을 지운다.
  - 안내 확인 기록은 주 계정에 없을 때만 복사한다.
  - DB 호출은 읽기 1 + 쓰기 3 이하다. 남은 호출이 모자라면 쓰지 않고 운영 이벤트 `merge_settings_carry_deferred` 를 남긴다. 실패하면 `merge_settings_carry_failed` 이고, 합치기 결과는 그대로다.
  - `performIdentityMerge` 의 맨 끝, 기존 뒤처리(세션·링크 표·방 연결·가계부별 표시 별명 정리)가 다 끝난 뒤에 남은 호출로만 한다. 그래서 기존 뒤처리의 예산과 순서는 V22.9.120 과 같고, 옮길 줄이 있든 없든 같은 호출·같은 운영 이벤트로 돈다. 부르는 쪽(관리자 통합·계정 잇기)은 그 뒤에 DB 를 쓰지 않는다.
  - 처음에는 링크 표·방 연결 정리보다 앞에 두었다(그 정리는 통합 리다이렉트라는 대비책이 있지만 설정 줄은 없다고 보아서). 독립 검토 1차가 링크 표 정리가 밀릴 수 있다고 짚어 링크 표 몫 4회를 남겼고, 2차가 방 연결(5회)·별명 정리 몫은 여전히 먼저 쓴다고 짚었다. 방 연결 정리가 밀리면 그 방의 연결 주인이 보조 계정으로 남고, 별명 정리가 밀리면 보조 계정의 표시 별명이 남는다. 그래서 맨 끝으로 옮겼다. 옮기기가 미뤄지면 관리자가 주 계정에 후원자 표시를 다시 켜고, 약관 안내 띠는 한 번 더 뜬 뒤 닫으면 끝난다.
  - 검사 2c 는 보조 계정이 방 연결 주인이고 가계부 표시 별명도 있는 장면을 예산 19가지로 돌려, 옮길 줄이 있을 때와 없을 때의 옮기기 밖 호출과 정리 이벤트가 같은지 본다. 첫 초안과 1차 반영본은 둘 다 실패한다.
- 남음: 이 판 전에 합친 계정은 그대로다. 2026-11-13 운영자 본인의 계정 잇기도 운영 V22.9.120 에서 했다. 후원자 표시가 있었다면 관리자 화면에서 다시 켜고, 안내 띠는 한 번 닫으면 끝난다.
- 검사: `validation/validate-supporter-carry-v229121.mjs`.

### S-3 개인정보처리방침 6절에 후원 항목이 없음 (P2, 고침)
- 무엇: 후원 확인 때 받는 정보(보낸 분 이름·보낸 날짜·계정을 가리키는 번호), 후원자 표시 기간, 공개 명단 이름이 6절 처리 항목 표에 없었다.
- 고침:
  - 6절 표에 ‘회원 번호’ 줄을 더했다. 항목은 회원 번호(MB- 로 시작, 계정마다 이미 있는 내부 식별값으로 만든 번호)와 그 번호가 가리키는 계정이다. ‘내 계정·보안’ 화면을 열 때나 운영자가 후원 확인·문의 때 그 번호로 계정을 찾을 때 기억 줄로 남고, 번호로 계정을 찾는 데만 쓴다. 보관은 회원 이용 기간이다. ‘MB- 로 시작’ 을 적어 같은 절의 ‘카카오 회원번호’ 와 구분했다.
  - 6절 표에 ‘후원(원하는 분만)’ 줄을 더했다. 항목은 후원자 표시 기간, 확인 메모(보낸 분 이름·보낸 날짜처럼 후원 확인에 쓴 내용), 공개 명단 이름이다. 후원 사실을 메일이나 오픈채팅으로 알려 줄 때 보낸 분 이름·보낸 날짜·회원 번호로 확인한다. 후원자 표시를 지울 때까지 보관하고, 알려 준 메일은 8절의 문의 메일 기준을 따른다. 오픈채팅으로 알려 준 내용은 그 대화방(카카오톡 오픈채팅)에 남아 카카오톡의 대화 보관 방식을 따른다.
  - 쿠키 목록에 `ab_sp`(S-4)를 더했다.
  - 12절의 V22.9.118 문단 끝에, 같은 날(2026-11-13) 개정에 후원 확인 방법도 들어 있다는 문장을 더했다. 그 문단과 같은 조건(공고일 = 시행일)일 때만 보인다. 회원 번호는 이미 있는 내부 식별값으로 만들고, 이용자에게서 새로 받는 정보가 없으며, 후원 확인과 문의에만 쓰므로 불리하지 않은 변경이라고 적었다.
  - 통합 커밋의 초안은 회원 번호를 후원 줄의 ‘알려 주신’ 항목으로만 적고, 12절에 ‘새로 받는 항목이 아니라 처리 내용을 더 자세히 적은 것’ 이라는 문단을 조건 없이 따로 두었다. 독립 검토 1차가 두 가지를 짚었다. 하나는 실제 저장(기억 줄·관리자 메모)과 맞지 않는다는 것이고, 다른 하나는 다음 개정 때 이 문단만 남는다는 것이다. 그래서 위처럼 고쳤다.
  - 독립 검토 2차가 회원 번호 줄의 ‘언제’ 에 운영자가 번호로 찾을 때 생기는 기억 줄이 빠졌고, 오픈채팅으로 알려 준 내용의 보관 설명이 없다고 짚어 두 칸을 고쳤다.
- 검사: `validation/validate-supporter-id-v229121.mjs`, `validation/validate-v22995-legal.mjs`.

### S-4 후원자 포인트 색이 세 화면에만 보임 (P3, 고침)
- 무엇: 포인트 색은 보는 사람의 후원자 표시를 읽는 세 화면(홈·전체 메뉴·참여자)에만 그렸다. 리포트·분석·설정 같은 다른 셸 화면은 컬러톤만 보였다. 전체 메뉴의 ‘고르면 컬러톤보다 먼저 보여요’ 가 그 화면들에서는 맞지 않았다.
- 고침:
  - 세 화면이 이미 읽은 값으로 쿠키 `ab_sp=1`(1일, HttpOnly·Secure·SameSite=Lax)을 주거나 지운다. DB 호출은 늘지 않는다.
  - 응답 마무리(`src/modules/my/supporter-accent.js`, `worker/router.js` fetch)가 로그인 쿠키와 `ab_sp=1` 이 함께 온 GET 의 셸 화면 HTML 에만 포인트 색을 붙인다. 공개·관리자·로그인 화면에는 붙이지 않는다.
  - 로그아웃과 세션이 바뀌는 응답은 쿠키를 지운다.
  - 이 쿠키는 보기만 바꾼다. 위조해도 위조한 사람 화면의 색만 바뀌고, 다른 사람이 보는 배지·명단은 서버가 설정 표의 표시로만 그린다.
  - 쿠키가 없는 응답은 바이트 그대로다.
- 검사: `validation/validate-supporter-carry-v229121.mjs`.

- 그 RPC 는 `on conflict (provider, user_id) do update set provider_subject = …` 다(저장소 정의). 그래서 강한 식별이 이미 다른 카카오 id 인 계정에서는 그 값을 덮어쓴다. 카카오 로그인이 둘인 계정은 마지막으로 로그인한 id 가 강한 식별이 된다.
- 두 id 모두 링크 표 별칭(provider kakao_login)이 있으면 어느 쪽으로도 같은 계정에 로그인되고, V22.9.117 잇기 확인도 둘 다 믿는다. 그래서 지금은 해가 없다.
- 별칭 없이 강한 식별만 있던 id 는 users.kakao_user_key 로만 찾는다. 그것도 없으면 다음 로그인이 새 계정을 만든다.
- 다음 계정 판에서 운영 RPC 정의와 그런 계정이 있는지를 확인한다(운영 DB 읽기는 사용자 지목 뒤).
- 같은 진단에서 본 것이고 결함은 아님: Aside 브라우저에 로그인된 카카오 계정으로 잇기를 확인하면 `kakao_account_mismatch` 가 나온다. 그 카카오 id 는 운영자 웹 계정의 카카오 로그인이 아니기 때문이다. 잇기는 사용자가 PC 보통 브라우저에서 끝냈다.
