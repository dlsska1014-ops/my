# V22.9.77 작업 중 새로 찾은 항목

아직 확인하지 못한 전제다. 이 문서는 발견 기록만 두고, 상태·고친 판·검사는 `docs/codex/FINDINGS_LEDGER.md` 의 `V77:` 행에서 추적한다.

- **N-2** (P3) ‘커피 4500 KB국민카드’의 메모가 ‘커피 KB’ — 결제수단 이름을 일부만 지운다(국민체크카드→‘국민’, 현대 카드→‘현대’, 삼성 페이·토스페이→‘페이’도 같음).
- **N-3** (P3) ‘지난 금요일 회식’의 메모가 ‘지난 회식’ — 요일 앞의 지난·저번·이번·다음(‘주’ 없이)을 지우지 않는다.
- **N-4** (P3) 카카오 저장 답장의 ‘지출자:’ 줄과 웹의 지출자 입력 목록은 아직 원래 별명(‘카카오사용자’)을 쓴다. B-5 의 구분 이름(‘카카오사용자 1’)을 쓰려면 5초 응답 경로에 조회가 하나 는다.
- **N-5** (P3) 같은 이름 가계부가 역할·만든 날까지 같으면 고르는 목록과 저장 답장에서 구분되지 않는다. 단톡방 새 참여자의 첫 기록 답장은 구분 표시 없이 이름만 보일 수 있다(D-6 남은 것).
- **N-6** (P2) V22.9.76 까지의 코드가 appUserId 로 만든 사용자 이름(예: ‘2265’)과 다른 계정으로 옮긴 `kakao_login:*` 별칭이 운영 데이터에 남아 있을 수 있다. V22.9.77 은 새로 생기지 않게만 막고 이미 생긴 것은 고치지 않는다. 운영 DB 를 조회해야 안다.
- **N-7** (P2) appUserId 가 웹 카카오 로그인 회원번호와 같은 번호 체계인지(봇 채널의 연결 앱이 웹 로그인 앱인지) 확인되지 않았다. 채팅으로 먼저 가입(V22.9.28)과 B-7 수정이 이 전제에 기댄다. 카카오 디벨로퍼스와 챗봇 관리자센터에서 연결 앱을 확인한다.
- **N-8** (P3) 관제 1.2.0 의 D1 조회(`json_extract`, `?1` 번호 인자, CTE)는 Node SQLite 로만 확인했다. 배포 뒤 첫 5분 수집에서 확인한다.
- **N-9** (P3) 따라잡아 넣은 기록이 든 주간 리포트 스냅숏은 다시 만들지 않는다(M-8 은 월간만).
- **N-10** (P3) 정기 규칙 수정 경로에서 지난달 리포트 다시 만들기가 실패하면 운영 이벤트로만 남고, 다음 예약 실행이 이어서 만들지 않는다.
- **N-11** (P3) 웹 화면 쪽 결제수단 판정 사본(`src/modules/client/legacy-ui-runtime.js`)은 N-1 수정 전 그대로라, 저장 전 미리 보기에서 ‘토스트’를 토스로 보일 수 있다(저장 결과는 서버 판정이라 맞음). 1년 캐시 자산이 바뀔 수 있어 이번 판에서 손대지 않았다.
- **N-12** (P3) ‘지난 금요일’처럼 ‘주’ 없이 쓴 요일 말은 가장 최근의 그 요일(그날이 오늘이면 오늘)로 읽는다. V22.9.76 과 같은 동작이며, ‘지난’이 지난주를 뜻해야 하는지 운영자가 정한다.
- **N-13** (P3) ‘교통카드 충전’의 메모가 ‘교통 충전’이 되고, 띄어 쓴 ‘카드 지갑’·‘신용 회복’은 결제수단을 정한다. 허용 목록(`AB_PAYMENT_WORD_END`)에 없는 붙여 쓴 동사 뒤의 결제수단은 읽지 않는다.

2026-10-24 추가 — ASIDE 운영 점검(관제 토큰 확인 실패)과 ASTRA 소스 분석(V22.9.76·V22.9.77 후보)에서 찾은 항목.

- **N-14** (P2) 관제의 분석 토큰 확인이 `redirect: "error"` 로 요청을 보낸다. Workers(workerd)의 fetch 는 redirect 로 `follow`·`manual` 만 받고 나머지는 TypeError 로 거절하므로, 토큰이 정상(Active, 2027-10-23 만료)이어도 관제는 늘 `token_user_transport` 를 남겼다(2026-10-23 21:00, 10-24 00:00 실측). 같은 api.cloudflare.com 의 사용량 수집은 그 값을 쓰지 않아 성공했다. 운영 관제 1.1.2 와, 1.2.0 으로 옮긴 같은 코드에 있다.
- **N-15** (P2) 관리자 JSON 백업이 분류·키워드(`fetchCustomCategories`)와 구성원 별명(`fetchMemberAliasMap`)의 읽기 실패를 빈 목록으로 바꾼다. 운영은 분류 표가 없는 모드라 분류·키워드가 모두 설정 값에서 오므로, 설정 조회가 한 번 실패하면 기본 분류만 든 파일이 200 으로 내려받아진다(V22.9.34 S10 규칙 위반). V22.9.76·77 공통.
- **N-16** (P2) 정기 반영(`fetchRecurringCronRows`)이 규칙 목록을 500개 한 쪽만 읽고 꽉 찼는지 보지 않는다. 건너뛴 규칙(조회 전용·차단된 지출자, 저장 거절)은 표식이 그대로라 매번 앞쪽을 차지하고, 지정일 순 정렬이라 이른 날짜의 막힌 규칙이 뒤 규칙을 밀어낸다. 그래도 남은 규칙 0 으로 끝나 checked_date 가 오늘로 넘어가므로 말일에 밀린 규칙은 다음 달 따라잡기에서도 빠진다. V22.9.76·77 공통, 지금 규모에서는 생기지 않는다.
- **N-17** (P3) V22.9.77 M-8 의 다시 만들기 대기(`report_rebuild`)가 300개를 넘으면 저장할 때 잘라낸다. 잘린 가계부는 지난달 기록과 표식이 이미 들어간 뒤라 다시 대기에 오르지 않아 스냅숏이 예전 금액으로 남는다. 넘침 알림도 메모리에만 남는다(N-18).
- **N-18** (P2) 예약 실행 결과(적용·실패·남은 건수)와 운영 이벤트(`scheduled_error`, `free_report_rebuild_failed` 등)는 인스턴스 메모리에 최근 220개만 남는다. 예약 실행은 화면 요청과 다른 인스턴스에서 돌 수 있어 다음 날 확인의 근거가 되지 못한다(V22.9.76 다음 날 확인이 [blocked] 된 원인).
